# Context Optimizer

目标是用更少、更聚焦的上下文换同等或更好的效果。成本和注意力是同一件事的两面：每一段常驻内容都要每轮付费，也都在分走模型的注意力。

## 第零步：确认上下文够不够

开始分析前先判断信息是否足够，不够就先列出缺什么，再继续。先区分对象，因为两类对象的数据来源不同：

| 对象 | 识别信号 | 数据从哪来 |
|---|---|---|
| A. 自研 Agent 产品 | 用户贴了 system prompt、Agent 配置、产品指标，或说的是"我们的客服 Agent / 某应用的 prompt" | 用户提供。缺失时按下方清单逐项要 |
| B. 本机 Claude Code / Codex | 提到 CLAUDE.md、AGENTS.md、rules、skills、MCP、output style、`~/.claude`、"我的配置" | 自己量。读 `references/measure-local.md` |

A 类需要的输入（缺哪项就问哪项，问之前先看会话和文件里是否已有）：
- 项目类型和目标
- 完整的系统提示词或 Agent 配置（片段只能做片段级结论）
- 冷启动数据：新会话或新用户占比、首轮成功率、平均冷启动轮次
- 前缀数据：系统提示加历史消息的平均 token 数、前缀占比、主要来源
- 约束和优先级：成本、延迟、效果哪个排第一

数据缺一部分不阻塞分析。没有冷启动指标时仍能对提示词本身做前缀和噪音分析，只是要在结论里写明"缺 X，以下判断基于最小假设 Y"。真正阻塞的只有一种情况：连要优化的提示词或配置本身都没有。

B 类不要问用户要数字，自己去量。量不到的项（例如 headless 测不出的 skill 清单）按 `measure-local.md` 的口径推算并标注。

**数字纪律**：每个数字都标来源，写成「实测」「用户提供」「推算」三者之一。不编造未给出的数据，也不把推算写成实测。

## 第一步：冷启动与平均前缀

读 `references/cold-start-prefix.md`。它列出前缀的构成项、缓存机制对成本的真实影响，以及冷启动的常见病灶和对应动作。

1. 先给现状：前缀构成（每项多少 token、占比、是否稳定可缓存）和冷启动表现。B 类附上测量命令和结果摘要。
2. 按 ROI 从高到低列优化清单。
3. 直接执行，给出优化后的内容。只改必要部分，保持原文风格。

## 第二步：注意力噪音

第一步完成并给出产物后再进入这一步，在第一步的优化版上继续改。读 `references/attention-noise.md`，按其中的噪音类型逐项排查。

1. 每个噪音点都要指出原文位置（引用原句或给出 `文件:行号`），写在表格的「问题」列里，不写"整体略显冗长"这类无法定位的判断。B 类要真正逐个读常驻文件（CLAUDE.md、rules、MEMORY.md、启用的 output style）并用 `rg` 对照原句，不能只凭字符数下结论。
2. 按 ROI 从高到低列优化清单。
3. 直接执行，给出进一步优化后的版本，并逐处说明这次修改如何降噪或聚焦。

两步之间有依赖：第一步可能已经删掉部分噪音，第二步不要重复计功。

两步结构对 A、B 两类和"只出报告"的请求都成立，不要把两张清单合并成一张。用户说"先别改文件"时，"直接执行"的含义是给出改写后的文本段落，而不是去改文件。某一步确实没有可做的，就写明逐项排查过哪些类型、为什么没有命中。

## ROI 怎么排

ROI 看四个因素：效果提升幅度、实现成本、token 成本影响、风险。排序时先看风险是否可接受，再在可接受的项里比收益和成本。不要算一个假精确的分数，用高、中、低三档并写出一句理由即可。几条经验判据：

- 对每轮都重复的固定前缀，1k token 的削减乘以轮数才是真实收益。只出现一次的内容削得再多也收益有限。
- 稳定且已命中缓存的前缀单价约为全价的十分之一。砍它的成本收益比通常不如治理不稳定前缀（导致缓存失效）或长会话历史。
- 删掉一条约束的风险是行为退化，而且往往不会立即暴露。凡是删减行为约束，风险至少记为"中"，并说明怎么发现退化。
- 合并或改写带来的风险低于删除；把常驻内容改为按需加载，介于两者之间。

清单短是正常结果。现状已经健康时就说健康，并说明依据，不为凑条数去改健康的内容。

## 输出格式

- 使用清晰的标题和表格。
- 两个优化清单都用表格，固定四列：`优先级 | 问题 | ROI 理由 | 具体优化动作`。不要另加列，原文位置、噪音类型和数据来源都写进对应的格子里。
- 执行部分给出完整、可直接复制的优化后内容。B 类涉及多个文件时，逐文件给出改动后的完整段落；用户要求直接修改文件的，先备份，再改，最后说明备份位置和改动摘要，不重复粘贴整份文件。
- 最后用 3 到 5 句话总结本次优化的核心收益和剩余风险。收益里的数字同样要标来源。

## 执行边界

- A 类只产出文本，不替用户改线上配置。
- B 类修改 `settings.json` 时用 `jq` 改单个字段，改完对比 hooks 挂载数、env 数和 permissions 数，确认没有静默丢项。修改 `~/.claude/rules/` 时遵循 rule-pruning 的做法：先列出候选并请用户拍板，确认后移入 `~/.claude/_archived_rules/`，不直接删除。
- 声称"前缀减少了 N"之前必须有改前和改后两次测量。没有测量就写成"预计减少约 N（推算）"。
