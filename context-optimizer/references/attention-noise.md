# 第二步方法卡：注意力噪音

噪音指的是会分走模型注意力、却不改变正确行为的内容，也包括会把模型往错误方向拉的内容。判断标准只有一个：删掉或改写这段内容后，模型在真实任务上的行为是否会变差。不会变差的就是噪音。

每个噪音点都要引用原文位置。只能说出"感觉有点啰嗦"、指不出具体哪句的，不算发现。

## 1. 噪音类型清单

| 类型 | 判据（命中才算） | 证据怎么拿 | 动作 |
|---|---|---|---|
| 冗余指令 | 同一约束在两处以上出现，措辞不同但意思相同 | 用 `rg` 搜关键词，逐处对照原文。不要凭"好像看过"下结论，删除前必须 grep 到原句 | 只保留一处，放在离使用场景最近的位置 |
| 与内置提示重复 | 自定义内容重复了平台内置系统提示已有的约束。Claude Code 的内置节包括 Delivering work、Corrections、Harness，以及编码相关指令 | 对照当前会话系统提示里的实际节标题和原文 | 删除重复部分。内置只给了下限时，自定义里只补上限 |
| 规则冲突 | 两条规则在同一场景给出相反指令，或者需要第三条仲裁规则才能裁决 | 列出冲突的两句原文和触发场景 | 合并成一条带条件的规则，删掉仲裁规则 |
| 模糊表述 | 含"适当、合理、尽量、优雅、必要时"一类无法做二值判断的词，又没有给判据 | 原句引用 | 改成可判定的条件或阈值；确实只能靠手感的，换成一个具体范例 |
| 多重目标竞争 | 同一段提示同时要求互相拉扯的目标（又要详尽又要简短，又要自主又要每步确认），却没有说明优先级 | 列出冲突目标 | 写明优先级和切换条件 |
| 强调语气堆叠 | 大量 MUST、IMPORTANT、绝对、必须，或者连续加粗和大写。强调过多时，真正关键的约束反而不突出，模型也可能对普通约束过度执行 | 统计强调词数量和位置 | 只给真正不可违背的少数几条保留强调，其余改为平实陈述并解释原因 |
| 无关示例 | 示例与当前任务分布不符，或者多个示例教同一件事；示例里的偶然特征（长度、措辞、话题）被模型模仿 | 对照示例和真实输入分布 | 删除同类重复，保留覆盖不同边界的示例，并说明示例里哪些特征不需要模仿 |
| 过长前缀里的关键约束被埋没 | 关键约束藏在长段落中间，前后都是背景介绍 | 指出该约束的位置和前后篇幅 | 把关键约束放到靠前或单独成段的位置，背景压缩或改为按需加载 |
| 失效规则 | 规则描述的场景、工具、路径已不存在，或者规则要求的产物长期没有出现 | 能计数的就计数（字段覆盖率、生成文件、日志），不能计数的检查引用对象是否还存在 | 删除或改为实际被遵守的那个子集。不要用加重措辞去"救"一条长期没人遵守的规则 |
| 角色和身份堆砌 | 长篇人设、头衔、性格描写，却不对应任何具体行为差异 | 问自己：删掉这段，哪个具体行为会变 | 删掉或压成一句真正影响行为的定位 |
| 格式标签噪音 | 为结构而结构的 XML 标签、编号体系、诊断标签残留在提示正文里 | 原文引用 | 只在需要模型区分输入块或解析输出时保留标签 |
| 过度具体的个案规则 | 为某一次历史事故写的规则，不具备复用性 | 看规则是否只描述了一个具体实例 | 移到记忆或案例库，不在常驻提示里占位 |
| 否定式指令过多 | 大量"不要做 X"，却没说该做什么 | 统计 | 改写成正向指令，只保留确实需要的禁止项 |

## 2. 评估风险的方式

删减行为约束的风险在于退化可能不会立即暴露。在优化清单的 ROI 理由里写清两件事：

- 这条内容原本防的是什么问题。
- 删掉或改写之后，怎么发现问题回来了。可以是某条回放样本、某个可数的产物，或者一类用户反馈。

如果说不出原本防什么，它很可能就是噪音，可以放心删。如果它防的是一个后果严重、却很少发生的问题，即使看起来冗余也要保守处理，优先选择改写而不是删除。

## 3. 本机 Claude Code 资产的特殊处理

- `~/.claude/rules/` 的删减遵循 `~/.claude/guides/rule-pruning.md`：先列候选，由用户逐条拍板，确认后移入 `~/.claude/_archived_rules/`。
- 社区软链 skill（`~/.claude/skills/` 下带 `->` 的条目）和 plugin skill 的本体会被更新覆盖。它们的噪音问题写在 `~/.claude/CLAUDE.md` 的消歧节，不改本体。
- output style 启用时必须保留 `keep-coding-instructions: true`，否则内置编码指令会整段丢失且不报错。
- 修改 skill 的 description 时，值里不要出现「空格加 #」，YAML 会从那里静默截断。

## 4. 修改说明的写法

第二步的执行部分逐处说明每次修改降低了哪一类噪音、聚焦到了什么。说明写在正文之外，不要把"[删除冗余]"这类标签写进优化后的提示词。
