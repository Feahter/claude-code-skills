# E2E 测试质量审核

把"这个 E2E 写得好不好"从拍脑袋变成可对照、可打分、能定位到行的审核流程。E2E 测试的价值不在数量，在于**能否在最小维护成本下，持续稳定可信地捕获真实缺陷**——审核就是围绕这一点展开。

审核分两个对象，标准不同，先认清评的是哪个：

- **工程层** = 一整套 E2E 代码 / 套件 → 用 §一
- **用例层** = 单条 case → 用 §二 + §三

## 审核流程

1. **定对象**：评整套代码还是单个 case？选对应标准维度。
2. **逐维对照**：单 case 用 §三评分卡逐项给分；整套代码用 §一七维 + §五三问定性。
3. **命中反模式就记账**：不要只说"稳定性差"，要定位到具体文件和行，例如 `cart.spec.ts:42 用了 sleep(3000)`。没有定位的批评对修复没用。
4. **出结论**：给判级（标杆 / 保留 / 重构 / 删除）+ **最小改进项**。改进项要可执行，不堆"建议提升可维护性"这类正确的废话。
5. **评覆盖度时**：按 §四，先穷举阻断风险点，再反查 case 是否覆盖——而不是先数 case 再凑覆盖率。

最后用 §审核报告模板 输出。

## 开审前：输入不全怎么办

实际评审时输入常常残缺，按下面分支处理——不卡住，也不瞎补：

| 情况 | 怎么办 |
|---|---|
| 只给截图 / 文字描述，没有代码 | 评能评的维度（失败现象、断言强度），其余维度标注"代码未提供，无法判断"，不臆测实现 |
| 代码片段不完整（缺 setup / Page Object / 配置） | 只评已给部分；改进项里点明"需结合 X 才能最终确认"，不对缺失部分外推 |
| 分不清评的是套件还是单 case | 默认按单 case 评（§二 + §三），并在结论里写明这一假设，让用户纠正 |
| 一批 case 要逐个评 | 先用 §三评分卡批量打分排序，只对 < 60 分的展开详评，不逐条套全模板 |

**轻量分流**：单条 case 只输出 §模板的精简形态（结论 + 评分 + 最小改进项）；唯有评**整套套件**才动用 §一七维 + §四覆盖度 + §五三问的全套流程。别对一条 6 行的 case 做整套体检。

## 一、工程层：一整套 E2E 代码

每一维给"优秀标准"和"反模式"。审代码时逐维扫，命中反模式即记录位置。

| 维度 | 优秀标准 | 反模式（命中即扣分） |
|---|---|---|
| **稳定性**（最重要） | Flaky 率 < 1–2%；每次失败都对应真实缺陷或环境变更 | 习惯性点 Retry 掩盖问题；`sleep(3000)`/`cy.wait(3000)`/`waitForTimeout` 硬编码等待；依赖执行顺序或前序残留数据 |
| **可维护性** | Page Object / App Action 分层，选择器集中管理，UI 改动只改一处 | 选择器散落在用例里；改个按钮要动几十个文件 |
| **选择器健壮性** | `data-testid`/`aria-label` 等语义化定位 | 绝对 XPath、易变 CSS 类名、文案字面匹配（文案一改就挂） |
| **执行效率** | 单 case 核心链路 < 30s，全量 CI < 15–20min，支持并行；能用 API 造数就不走 UI 铺垫 | 串行强依赖；UI 点几十步铺数据；总耗时随 case 数指数增长 |
| **可诊断性** | 失败自动截图 / 录屏 / trace / 网络日志，报告能定位到具体断言步骤 | 只抛一句 `TimeoutError: waiting for selector...`，排查全靠猜 |
| **覆盖有效性** | 用**用户旅程覆盖率**衡量（核心转化漏斗、资损场景），而非代码行覆盖率 | 追求 100% 覆盖；用 E2E 测页脚版权年份这类该下沉到单测的细节 |
| **可读性** | Given-When-Then / AAA（Arrange-Act-Assert）结构，测试名自描述业务行为 | 一堆 `click('#btn1')` 式裸操作，看不出在测什么 |

## 二、用例层：单条 case 的黄金标准

### 必须满足（缺一不可）

这五条任意一条不达标，case 就该重构或删除——五份来源高度一致地把它们列为底线。

| 维度 | 标准 | 怎么验 |
|---|---|---|
| **原子性** | 一个 case 只验证一个业务场景 / 断言 | 失败时能否一句话说清问题？ |
| **独立性** | 不依赖执行顺序；自造数据，自带 setup/teardown | 随机打乱执行顺序仍能过？ |
| **确定性** | 相同代码 + 环境结果恒定，永不 flaky | 连跑 50 次是否全过？ |
| **业务价值** | 失败 = 用户无法完成核心任务（高 ROI） | 删掉它，上线风险是否可接受？ |
| **强断言** | 验证业务结果（订单状态 / 金额 / 库存 / 邮件），而非 UI 表面"出现成功二字" | 断言点集中在 1–3 个关键结果上？ |

### 进阶（区分"优秀"与"合格"）

- **语义清晰**：标题是完整业务描述（`用户登录后下单并用优惠券应正确扣减金额`），而非 `test coupon`。
- **分层断言**：断言中间关键节点（订单状态流转、金额计算过程），不只验最终态。
- **防御性**：对已知不稳定因素（如第三方支付回调）用重试 / mock，而不是直接 skip 掉验证。
- **诊断友好**：失败信息带上下文，如 `expected price 99 but got 199, coupon CODE2026 not applied`，让非测试人员看日志就能还原现场。

## 三、量化评分卡（单 case 满分 100）

需要给出分数时用这张卡，每维独立打分后求和：

| 维度 | 分值 | 看什么 |
|---|---|---|
| 业务价值（失败影响面） | 30 | 失败是否意味用户无法完成核心任务 |
| 稳定性（flaky 率） | 25 | 是否含硬编码等待 / 顺序依赖 / 未 mock 的外部依赖 |
| 执行速度 | 15 | 是否有多余 UI 铺垫、能否 API 造数 |
| 可维护性（耦合度） | 15 | 选择器是否集中、UI 改动波及面 |
| 诊断效率（失败信息质量） | 15 | 失败时能否直接定位根因 |

判级：

- **< 60 分** → 重构或删除
- **60–80 分** → 优化后保留
- **> 80 分** → 团队标杆

## 四、覆盖度评估（判断"测全没漏"）

覆盖全不是"测了很多"，而是**每个失败都对应一个已知的兜底机制**。

**三层验证法**——逐层问"这层验了吗"：

| 层级 | 验证什么 | 通过标准 |
|---|---|---|
| 功能层 | 正向主链路 | 核心价值路径 100% 跑通 |
| 防御层 | 反向 / 异常分支 | 每个分支有明确的降级或报错 |
| 数据层 | 状态一致性 | 失败后数据不脏、可恢复 |

**覆盖度指标**：

```
覆盖度 = 已验证的阻断风险点 / 已识别的阻断风险点 × 100%
```

`≥ 95%` 视为覆盖全（留 5% 给未识别的黑天鹅），`< 90%` 有明显盲区。

**关键动作**：先用 FMEA 思路穷举风险点（主链路每个节点"挂了用户会怎样"、每个外部依赖的失败、数据边界、权限越界），再反查 case 是否覆盖。顺序反了就会"为凑覆盖率而写 case"，漏的恰恰是没想到的那些。

## 五、灵魂三问（无需打分、快速定性时用）

1. 流水线变红时，团队第一反应是"又有 bug 了"还是"测试又抽风了"？→ 测**稳定性**
2. UI 变动时，改测试代码的时间是否超过了写业务代码？→ 测**可维护性**
3. 删掉一半 E2E case，上线时心里会不会发慌？→ 测**业务价值**

三问全过，套件基本健康；任意一问答案不妙，对应维度就是治理重点。

## 审核报告模板

输出审核结论时用这个结构，保持一致、可对比：

```markdown
# E2E 质量审核：<对象名>

## 结论
判级：<标杆 / 保留 / 重构 / 删除>（单 case 附评分：XX/100）
一句话：<这份测试当前最大的问题或最大的价值>

## 逐维打分 / 命中反模式
| 维度 | 评价 | 定位 |
|---|---|---|
| 稳定性 | ... | cart.spec.ts:42 sleep(3000) |
| ... | ... | ... |

## 最小改进项（按性价比排序）
1. <具体、可执行的一条>
2. ...

## 覆盖度（如评的是套件）
已识别阻断风险点 N 个，已覆盖 M 个，覆盖度 M/N。盲区：<列出未覆盖的风险点>
```

## 落地与迭代纪律

审核结论给完，若用户在搭 / 治理套件，补这几条建议：

- **从核心起步**：先用 5–10 个核心用户旅程建标杆库，再逐步扩展，别一上来铺全量。
- **阈值随成熟度收紧**：flaky 率目标先 `< 2%` 再 `< 1%`；评分判级线按团队实际调。
- **定期治理**：删掉低价值、常年 skip / 注释掉的 case，别让它沦为历史包袱。
- **协作定标**：核心场景由开发 / 测试 / 产品共同认定——断言语义人工定义，执行交给自动化。
