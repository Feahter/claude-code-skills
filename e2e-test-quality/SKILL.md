# E2E 测试质量审核

把"这个 E2E 写得好不好"从拍脑袋变成可对照、可打分、能定位到行的审核流程。E2E 测试的价值不在数量，在于**能否在最小维护成本下，持续稳定可信地捕获真实缺陷**——审核就是围绕这一点展开。

审核分两个对象，标准不同，先认清评的是哪个：

- **工程层** = 一整套 E2E 代码 / 套件 → 用 §一
- **用例层** = 单条 case → 用 §二 + §三

## 标准来源：单一事实源在 playbook

**本 skill 只负责"怎么评"（评分卡、判级、覆盖度算法、报告格式），不重复定义"什么是好写法"。** 具体的选择器优先级、断言规范、flaky 分类、分层归属，一律以 `~/.claude/skills/playbook/references/` 为准——审核时按需 Read，不凭记忆下判断：

| 判断什么 | 权威文档 |
|---|---|
| 选择器该用哪种、哪些绝不能用 | `playbook/references/selectors.md` |
| 断言强弱、web-first、禁死等待 | `playbook/references/assertions.md` |
| flaky 归因与修法 | `playbook/references/flaky.md` |
| 这条 case 该不该留在 E2E 层 | `playbook/references/architecture.md`（E2E 黑名单）+ `test-pyramid.md` |
| 覆盖盲区怎么穷举 | `playbook/references/adversarial-coverage.md`（6 维度清单） |
| 测试为何腐烂、脆弱度指标 | `playbook/references/anti-rot.md` |
| CI 分片、artifact、门禁分层 | `playbook/references/ci.md` |
| trace 怎么读、失败怎么定位 | `playbook/references/trace-debug.md` |

playbook 是写测试的引擎，本 skill 是评测试的尺子。**同一条规则出现分歧时以 playbook 为准**，并顺手修正本文（说明依据），别两边各留一份慢慢漂移。

## 审核流程

1. **定对象**：评整套代码还是单个 case？选对应标准维度。
2. **逐维对照**：单 case 用 §三评分卡逐项给分；整套代码用 §一七维 + §五三问定性。
3. **命中反模式就记账**：不要只说"稳定性差"，要定位到具体文件和行，例如 `cart.spec.ts:42 用了 sleep(3000)`。没有定位的批评对修复没用。
4. **出结论**：给判级（标杆 / 保留 / 重构 / 删除）+ **最小改进项**。改进项要可执行，不堆"建议提升可维护性"这类正确的废话。
5. **评覆盖度时**：按 §四，先穷举阻断风险点，再反查 case 是否覆盖——而不是先数 case 再凑覆盖率。

最后用 §审核报告模板 输出。

## 开审前：输入不全怎么办

实际评审时输入常常残缺，按下面分支处理——不卡住，也不瞎补：

| 情况 | 怎么办 |
|---|---|
| 只给截图 / 文字描述，没有代码 | 评能评的维度（失败现象、断言强度），其余维度标注"代码未提供，无法判断"，不臆测实现 |
| 代码片段不完整（缺 setup / Page Object / 配置） | 只评已给部分；改进项里点明"需结合 X 才能最终确认"，不对缺失部分外推 |
| 分不清评的是套件还是单 case | 默认按单 case 评（§二 + §三），并在结论里写明这一假设，让用户纠正 |
| 一批 case 要逐个评 | 先用 §三评分卡批量打分排序，只对 < 60 分的展开详评，不逐条套全模板 |

**轻量分流**：单条 case 只输出 §模板的精简形态（结论 + 评分 + 最小改进项）；唯有评**整套套件**才动用 §一七维 + §四覆盖度 + §五三问的全套流程。别对一条 6 行的 case 做整套体检。

## 一、工程层：一整套 E2E 代码

七个维度。**"扫什么"是快速定位线索，判定尺度看对应的权威文档**——命中线索先记位置，再去文档确认它是真违规还是本项目的合理例外。

| 维度 | 扫什么（高频违规信号） | 判定依据 |
|---|---|---|
| **稳定性**（最重要） | `waitForTimeout` / `cy.wait(3000)` / `sleep`；本地开着 retries；用例间靠执行顺序或残留数据 | `flaky.md`（含"跑 10 次挂 1 次即 flaky"的判定线、六类归因占比）+ `assertions.md` 反模式禁令 |
| **可维护性** | 选择器散落在 spec 里而非 `tests/actions/`；spec 里直接是 30 行 UI 操作 | `architecture.md`（业务 DSL 四层、何时才引入 POM） |
| **选择器健壮性** | CSS 类名、`nth-child`、xpath、动态 hash className；testId 满天飞但没走 Role | `selectors.md`——优先级是 **Role > Label > Placeholder > Text > TestId**，testId 是最后兜底而非首选 |
| **执行效率** | UI 点几十步铺数据（该 API 造数）；单 case 核心链路 > 30s；CI 未分片 | `ci.md`（分片阈值表：用例数 ≥ 5 才上分片，目标 5–8 分钟/shard） |
| **可诊断性** | config 未开 trace / screenshot / video；失败只有一句 `TimeoutError` | `trace-debug.md`（trace 配置项 + 5 分钟定位流程） |
| **覆盖有效性** | 追代码行覆盖率；E2E 里测校验规则 / 格式化 / hover 样式这类该下沉的东西 | `architecture.md` 的 E2E 黑名单 + `test-pyramid.md` 分层判断；覆盖度用本文 §四 而非行覆盖率 |
| **可读性** | 测试名是 `test coupon` 而非业务描述；一堆 `click('#btn1')` 裸操作 | `architecture.md` 业务 DSL 命名规范（业务动词 + 业务对象） |

补充两个维度化的腐烂指标（`anti-rot.md`）：**测试脆弱度** = 过去 30 天无代码变更却失败的测试数；**测试维护比** = 每新增 100 行业务代码要改的测试行数，> 1:1 说明耦合过深。这两个数比任何定性描述都能说服人，能拿到数据就拿。

## 二、用例层：单条 case 的黄金标准

### 必须满足（缺一不可）

这五条任意一条不达标，case 就该重构或删除。

| 维度 | 标准 | 怎么验 |
|---|---|---|
| **原子性** | 一个 case 只验证一个业务场景 / 断言 | 失败时能否一句话说清问题？ |
| **独立性** | 不依赖执行顺序；自造数据，自带 setup/teardown | 随机打乱执行顺序仍能过？ |
| **确定性** | 相同代码 + 环境结果恒定，永不 flaky | 连跑 10 次是否全过（`flaky.md` 的判定线）？ |
| **业务价值** | 失败 = 用户无法完成核心任务（高 ROI） | 删掉它，上线风险是否可接受？ |
| **强断言** | 验证业务结果（订单状态 / 金额 / 库存 / 邮件），而非 UI 表面"出现成功二字" | 断言点集中在 1–3 个关键结果上？ |

判"独立性 / 确定性"是否真达标，别只看代码眼缘——`playbook/scripts/validate-test.sh` 能机械扫出死等、违规选择器、缺断言，跑得起就先跑，把机械项交给脚本，人只判业务价值和断言强度。

### 进阶（区分"优秀"与"合格"）

- **语义清晰**：标题是完整业务描述（`用户登录后下单并用优惠券应正确扣减金额`），而非 `test coupon`。
- **分层断言**：断言中间关键节点（订单状态流转、金额计算过程），不只验最终态。
- **防御性**：对已知不稳定因素（如第三方支付回调）用重试 / mock，而不是直接 skip 掉验证。skip 必须带 TODO + 复活条件（`anti-rot.md`），裸 skip 就是永久腐烂。
- **诊断友好**：失败信息带上下文，如 `expected price 99 but got 199, coupon CODE2026 not applied`，让非测试人员看日志就能还原现场。
- **关键按钮双模态**：支付 / 提交订单 / 弹窗确认这类"用户必须点得到"的元素，只断 `toBeVisible()` 不够——见 `assertions.md` 的双模态断言（语义 + 视觉 + 交互三层）。审到关键操作缺这层可提为改进项，但**不要要求普通元素都上双模态**，成本会爆炸。

## 三、量化评分卡（单 case 满分 100）

需要给出分数时用这张卡，每维独立打分后求和：

| 维度 | 分值 | 看什么 |
|---|---|---|
| 业务价值（失败影响面） | 30 | 失败是否意味用户无法完成核心任务 |
| 稳定性（flaky 率） | 25 | 是否含硬编码等待 / 顺序依赖 / 未 mock 的外部依赖 |
| 执行速度 | 15 | 是否有多余 UI 铺垫、能否 API 造数 |
| 可维护性（耦合度） | 15 | 选择器是否集中、UI 改动波及面 |
| 诊断效率（失败信息质量） | 15 | 失败时能否直接定位根因 |

判级：

- **< 60 分** → 重构或删除
- **60–80 分** → 优化后保留
- **> 80 分** → 团队标杆

## 四、覆盖度评估（判断"测全没漏"）

覆盖全不是"测了很多"，而是**每个失败都对应一个已知的兜底机制**。

**三层验证法**——逐层问"这层验了吗"：

| 层级 | 验证什么 | 通过标准 |
|---|---|---|
| 功能层 | 正向主链路 | 核心价值路径 100% 跑通 |
| 防御层 | 反向 / 异常分支 | 每个分支有明确的降级或报错 |
| 数据层 | 状态一致性 | 失败后数据不脏、可恢复 |

**覆盖度指标**：

```
覆盖度 = 已验证的阻断风险点 / 已识别的阻断风险点 × 100%
```

`≥ 95%` 视为覆盖全（留 5% 给未识别的黑天鹅），`< 90%` 有明显盲区。

**关键动作**：先用 FMEA 思路穷举风险点，再反查 case 是否覆盖。顺序反了就会"为凑覆盖率而写 case"，漏的恰恰是没想到的那些。

穷举风险点时用 `playbook/references/adversarial-coverage.md` 的 **6 维度清单**（异常路径 / 角色权限 / 网络异常 / 边界数据 / 并发 / a11y）当骨架，别现场自由联想——自由联想的盲区正是你想不到的那些。项目已跑过 playbook 的可以直接读 `.playbook/test-plan.md` 拿已识别风险点，或跑 `playbook/scripts/coverage-audit.sh` 得到 6 维度的现有覆盖分布，省掉手工穷举。

**分母的更好来源**：若项目跑过 `test-strategist`，直接用它策略包里的风险台账当分母——它除了 6 维技术维度，还含业务风险四维（影响面 / 变更频度 / 历史高发 / 可逆性）与每条风险的 `oracle`，比手工穷举准。此时覆盖度的判定变成两问：**每条 `disposition: test` 的义务有没有对应实现**（按 `risk_id` 反查），以及**实现的断言是否真的证明了该义务的 `oracle`**（断言弱于 oracle 等于没覆盖，这是最高发的假覆盖）。`monitor` / `design-fix` / `explore` / `accept` 的风险不计入 E2E 覆盖度分母，但要在报告里列出，说明它们由别的手段兜着。

它那份清单的取向是"该补哪些用例"，本文这里是"已识别的算不算覆盖到了"——同一份维度骨架，一个用于生成，一个用于验收。

## 五、灵魂三问（无需打分、快速定性时用）

1. 流水线变红时，团队第一反应是"又有 bug 了"还是"测试又抽风了"？→ 测**稳定性**
2. UI 变动时，改测试代码的时间是否超过了写业务代码？→ 测**可维护性**
3. 删掉一半 E2E case，上线时心里会不会发慌？→ 测**业务价值**

三问全过，套件基本健康；任意一问答案不妙，对应维度就是治理重点。

输出审核结论时用这个结构，保持一致、可对比：

```markdown

判级：<标杆 / 保留 / 重构 / 删除>（单 case 附评分：XX/100）
一句话：<这份测试当前最大的问题或最大的价值>

## 逐维打分 / 命中反模式
| 维度 | 评价 | 定位 |
|---|---|---|
| 稳定性 | ... | cart.spec.ts:42 sleep(3000) |
| ... | ... | ... |

## 最小改进项（按性价比排序）

2. ...

## 覆盖度（如评的是套件）
```

## 落地与迭代纪律

审核结论给完，若用户在搭 / 治理套件，补这几条建议：

- **从核心起步**：先用 5–10 个核心用户旅程建标杆库，再逐步扩展，别一上来铺全量。
- **阈值随成熟度收紧**：flaky 率目标先 `< 2%` 再 `< 1%`；评分判级线按团队实际调。
- **定期治理**：删掉低价值、常年 skip / 注释掉的 case，别让它沦为历史包袱。
- **协作定标**：核心场景由开发 / 测试 / 产品共同认定——断言语义人工定义，执行交给自动化。

## 审完之后：交给谁

本 skill 到"给出判级 + 最小改进项"为止，**默认只审不改**。改进项要落地时按目标分流：

- **重写 / 补 E2E 用例** → `playbook`（四阶段引擎，从 `.playbook/project.json` 探测起）
- **改进项判定"该下沉单测 / 集成"** → 同样交 `playbook`，走 `test-pyramid.md` 分层 + `unit-integration.md` 承接，别在 E2E 层硬修
- **审核时想看页面真实状态**（截图 / 控制台报错 / 选择器实际命中） → `webapp-testing`
- **测试代码本身的代码质量**（命名、重复、类型） → `cr-master`

反向：playbook 阶段 4 校验完想要一份质量基线或打分时，回调本 skill。

## 边界

- **只审 E2E**。单元 / 集成测试的评审标准不同（mock 边界、fixture 对齐、快照大小），走 `playbook/references/unit-integration.md` 和 `anti-rot.md`，不套本文的评分卡。
- **不排功能 bug**。用例失败到底是测试写错还是应用真有 bug，是 `diagnose` / `systematic-debugging` 的活。
- **不定义好写法**。任何"应该怎么写"的规则以 playbook references 为准（见开头的单一事实源表）。
- **不定义风险、不重算优先级**。风险台账、P0–P3 分级、处置决定由 `test-strategist` 独占。审核时发现某 P0 义务没落实，报「义务未落实」并引用 `risk_id`；对该风险**该不该是 P0** 有异议，走反馈让它改判，不在评分里自行降级或加权。三方决策权矩阵见 `~/.claude/skills/test-strategist/references/ownership.md`。
