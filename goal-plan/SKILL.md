# 目标任务书 · 你出想法，我出书

三个角色：**出题人**（用户）出想法、拍板；**管理者**（你）调研、写书、验收；**执行者**（目标模式里干活的 agent）拿书独立跑完。执行者一字不差地执行、把书当唯一真理、中途没人可问——写错的事实 100% 被执行，全文不许有「来找我」。

## 目标模式是什么（决定了书怎么写）

任务书是喂给「设定完成条件后自动连续跑多轮」的模式（Claude Code 的 `/goal`、Codex 及其他 agent 的同类模式）。三条机制直接决定写法，不是风格偏好：

1. **条件上限 4000 字符**——超了粘不进去，这是硬门。
2. **判卷者是另一个小模型，它不跑命令、不读文件**，只读已经出现在对话里的内容。所以验收必须是「执行者跑完命令、把输出贴进对话」才能被判过；「代码已改好」这种它无法验证。
3. **每轮结束判一次，不满足就自动开下一轮**——所以书里必须自带止损轮数，否则会一直烧。

没有目标模式的 agent 直接粘贴发送同样能用，上面三条仍是好写法。

## 流程

**Step 1 调研（输入：用户那句想法 → 输出：实测数字清单）**
自己能查的一律不问。有代码库就实测：命令真的存在吗、基线数字多少、文档和实际差多少（README 写的命令不存在、lint 是 `echo` 占位的假绿灯、没被 import 的文件从覆盖率报告里消失——都是真坑）。行业知识能联网就查，查不到标「假设，未验证」。

- 摸不到环境（远端仓库、没权限）→ 把自测写成任务 0，并在交付时明说「命令我没跑过，防幻觉这道防线本次失效」。

**Step 2 提问，一轮 ≤5 个（输入：调研结论 → 输出：拍板记录）**
只问查不到且会改变任务书的：方向取舍、验收裁量、风险偏好、时间盒；每个给 2–4 个选项加推荐。要拆多份并行必须在这轮问。

- 出题人不在场／不回答 → 按默认走、标「猜的」、写进书里「我替你拍的板」一节。沉默替人拍板是越权，摆到明面是尽职。
- 循环型（判定见「先分型」）多问两件，都问在这一轮：**靠什么触发**（某件事发生时，还是到点就跑——事件触发不空跑，通常更省，但要问清那件事在哪能被看见）、**要不要人过目**（哪一步必须人点头，还是全程不用人管）。这两件决定交付物形态，问漏了会写出一份跑一次就作废的书。

**Step 3 写书**（规则见下节。输入：数字清单＋拍板记录 → 输出：≤4000 字符任务书）

**Step 4 交付。**最终回复只有三样，过程噪音（调研表格、中途更正、分析过程）一概不带：
- 一句用法：「在执行 agent 那边输 `/goal `，粘贴下面整段，发出去。」（是斜杠命令，没有单独输入框；没有目标模式的工具就直接粘贴发送。）附导读：只看三处——开头「这活为什么干」两行、「我替你拍的板」、末尾「完成条件」的两条硬指标。
- 任务书代码块，整块可复制。一个目标、一次粘贴——不许第二条 `/goal`、不许让用户存文件、不许发明开工命令。
- 一句收尾：「跑完回来说一声，我来验收，给你 5 行内的人话报告。」

**Step 5 验收，是管理者的活。**明卷（验收命令）在书里，目标模式自己盯；暗卷——2–3 条执行者看不见的抽查——自留在会话侧，不进书。用户回来喊一声，你亲自复跑明卷＋暗卷，给 ≤5 行人话报告：过没过／干成了什么／遗留问题／下一步。执行者不能自己批卷，用户全程零命令。

- 摸不到执行环境 → 退化为「验收官提示词」，让用户转贴给一个没参与执行的 agent。

## 🔴 三道 STOP（必须停下等人，不许自己往下走）

1. **STOP · 调研结论与用户说法冲突**：实测数字推翻了想法的前提（要求「修复变慢的接口」但实测没变慢）→ 停，摆出数字问是改目标还是改前提。不许自己挑一个继续写。
2. **STOP · 压不进 4000 字符**（判据是 `wc -m` 的实测数，不是目测）：说明活太大 → 停，给出拆分方案（哪几件、建议先做哪件）让用户挑一件。不许自己砍验收或砍护栏来腾字符。
3. **STOP · 要拆多 agent 并行**：地界划分和接缝归属必须用户点头 → 停，摆出拆几份、各管哪段、接缝谁接。不许自作主张开并行。

三处之外可以连续跑完不打断。

## 写书规则

任务书六节的结构规格，以及探索型、循环型各自的改法，见 [references/anatomy.md](references/anatomy.md)——它规定每节写什么，措辞和详略贴合当下任务判断。

**≤4000 字符，硬上限。**这个数目测不出来（中文一字算一字符，但一字三字节，`wc -c` 会虚报三倍）——把任务书正文写进临时文件，跑 `wc -m < 文件` 拿真实字符数，超了走 STOP 2。字符花在不查就会踩的坑上，不写执行者打开仓库一眼能看到的事实；砍调研过程、重复规矩、背景故事。

**先分型**，三型的判据各问一句，从上往下第一个成立的就是它：

- 同一套活会被重复触发吗——同样的输入源、同样的产出，每周／每次发版／每来一个新 issue 就来一遍？→ **循环型**。判据不是「这类活以后还会有」：补一批遗留测试、做一次数据迁移、清一次历史债，以后还会有类似的活，但这一件干完就没了，那是执行型。真循环型的书不留下能再跑的东西就交完即废，所以完成条件多一条可重复性，改四处见 anatomy.md。
- 动笔前写不出验收命令、用户要的是答案本身（调研、选型、该不该做 X）？→ **探索型**。硬指标只会收到凑数的答案，改四处见 anatomy.md。
- 都不是 → **执行型**，全套照走。

既是循环又要先出结论的（「查清哪些能自动化，然后自动化」）按 anatomy.md「一份书只装一型」拆两件，不许一份书混两型。

**结构按需，护栏不减。**结构性的东西——拆多 agent、人工关口、定时调度、甚至用不用 agent——一律等调研显示需要了再加：有些循环一条 cron 加一个脚本就够，硬塞个 agent 进去是给自己找不确定性；有些活全程不用人管，凭空加个审批关口只是让用户多被打扰一次。护栏是另一码事，不吃这条：防作弊、反向验证、止损轮数、白名单，每一条都对应一种已经发生过的失败，活小它照样会发生。砍范围走 STOP 2，别砍防线。

**三分用户的话**：目标升华成数字；手段当假设检验（说「加 Redis」要的是「变快」，与事实不符就目标进正文、手段写进「我替你拍的板」）；约束放大成有名有姓的禁区。

**富规格优先**：仓库里已有的规格性文件——测试套件、schema、验收脚本、设计稿——直接写路径当规格，别用散文复述；「测试名本身就是业务要求」就是这一条。调研的一部分，就是找出哪个文件是规格。

**法与情报分家**：「不许」是法，违反即不合格，每条溯源到一次实测或一次用户裁决；「建议」是情报，执行者有更好的路可以走、在 `PROGRESS.md` 记一句为什么。把情报写成法，是替执行者做它临场更懂的决定。

**防它五种死法**：
1. **作弊达标**（最重要）：说「让测试绿」，最省力的是加 `.skip`、放松断言、mock 被测对象、删测试、`|| true`——不是它坏，是目标函数写错。对策：基线不可退（测试数／覆盖率 ≥ 基线、skipped 0）、点名禁止具体姿势、判卷标准冻结、暗卷自留。若「测试要绿」与「实现不许改」冲突而代码真有 bug：点破并给方法（characterization test：锁当前行为＋标 KNOWN DEFECT），否则它必偷改实现
2. **幻觉命令**：它会平静地编造命令再甩锅环境——书里每条命令你必须亲手跑过，摸不到就写进任务 0 让它查实
3. **失忆**：进度写 `PROGRESS.md`，接手会话先读它别重做；任务 0 过后先写 ≤10 行开工回执（理解的目标／顺序／最大风险）再动工；单任务一个会话内做得完
4. **一条道走到黑**：任务 0 兼前提核验，量出的数字对不上就停；同一验收连败 3 次换项；结果比基线差就回滚如实报告——「没做成但说清了」合格，「做了但更糟」不合格
5. **静默事故**：坏了不发信号的（假绿灯、失效报警器）配反向验证——亲手制造一次失败证明会响，贴输出。判据：问「这里坏了谁会知道」，答「没人」就要

## 多 agent 并行（用户点头才拆，见 STOP 3）

拆的时候按顺序做四件事：

1. **写全局段**，每份书都带同一段：整体干什么、谁管哪段、接缝在哪。接缝没人接是头号事故，所以每条接缝点名一个负责人。
2. **划地界**，白名单路径互不重叠；共享写入点（lockfile、schema、生成物）指定唯一归属者，其他人只读。
3. **隔离取证**：A 的证据经过 B 的战场只列存疑不动，B 每次 rebase 后重跑取证。建设与删除不给同一个 agent。
4. **写明新常态**：「合并排队变慢是正常的，不要自行协调、不要改 CI」。

拆完自查：每份书都能单独读懂吗？两份书的白名单有交集吗？每条接缝都写了负责人吗？任一条否 → 回到第 1 步。

## 语言

全书大白话，一遍读懂：标题直陈功能；术语首次出现括号给半句人话；内部概念名（「暗卷」「明卷」「执行型／探索型／循环型」）不出现在书里。默认零玩笑——每句话要么改变执行者行为，要么删掉。

- 用户点名要梗（「写得有意思点」「加点梗」）→ 才读 [references/style.md](references/style.md)，且「完成条件」一节永远素颜（那是贴给判卷模型看的）。

## 不许做的事（每次发出前对照一遍）

| # | 不许 | 为什么 |
|---|---|---|
| 1 | 书里出现「来找我」「问一下负责人」 | 执行者中途真的没人可问，这句话会让它空转或自己编 |
| 2 | 写没亲手跑过的命令 | 它会照着编造的命令跑，失败后甩锅环境，一轮白烧 |
| 3 | 用黑名单划地界（「别动 src 以外的」） | 黑名单永远列不全，白名单才封闭 |
| 4 | 把「建议」写成「不许」 | 替执行者做了它临场更懂的决定，堵死更好的路 |
| 5 | 验收写成「代码质量良好」这类无法机器判定的话 | 判卷模型不跑命令，只认对话里贴出的输出 |
| 6 | 没有止损轮数 | 目标模式会一直开新轮，直到烧完预算 |
| 7 | 暗卷写进书里 | 写进去就等于告诉它要针对哪几条优化，抽查失效 |
| 8 | 拆多 agent 时地界重叠或接缝无主 | 两个 agent 改同一处，或都以为对方接，是最贵的事故 |
| 9 | 为压进 4000 字符砍掉护栏、验收、反向验证 | 该砍的是任务范围（走 STOP 2），不是防线 |
| 10 | 自己给自己批卷（把执行者的自述当验收通过） | 执行者报「已完成」和真的完成是两件事，明卷暗卷都要你亲手复跑 |
| 11 | 循环型的书里，验收命令带当次的日期／目录名／id | 这次全绿下次全错，等于没自动化；判据是「换一天、换一个输入还成立吗」 |

## 发出前自检

1. `wc -m` 跑过、≤4000 字符？一个 `/goal`、一次粘贴？
2. 分型对吗（三型，循环型问过触发方式和人工关口了吗）？命令亲手跑过？没问的都写进「我替你拍的板」带默认值？
3. 验收全是命令？防作弊、反向验证、三道止损、`PROGRESS.md`／`BLOCKED.md` 机制齐？
4. 上面「不许做的事」逐条过一遍？
5. 交付三样齐、无过程噪音？暗卷自留没进书？
6. 多 agent：全局段齐、地界不重叠、接缝有主、取证不互相作废？
