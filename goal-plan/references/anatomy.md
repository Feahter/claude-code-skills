# 任务书 · 结构规格

六节，顺序固定：「我替你拍的板」放最前（发出前扫一眼就能改判），「完成条件」放最后（两条硬指标收拢一切）。整本 ≤4000 字符，单任务的书通常 1500–2000。本规格不配样文——照规格自己写，措辞贴合当下的任务，别套任何现成句式。

## 开头（不带标题，五件事各一句）

- 你是执行者，这份文档是你唯一的任务来源；中途没人可问，拿不准的写进 `BLOCKED.md`（待裁决清单），跳过继续做别的，最后随交付提交
- 断了、换新会话：先读 `PROGRESS.md`（进度记录）接着做，别重做；每做完一项立刻更新
- 这活为什么干：一句意图，为什么干＋干完世界什么样——书里没写到的情况，执行者靠它自己裁
- 两个要求打架时的让步顺序（如「算得对 > 做得全 > 做得快」）
- 死规矩与参考的分界：「只允许」「不许」违反算失败；「建议」有更好的路就走，在 `PROGRESS.md` 记一句为什么

## 我替你拍的板

没问出口的每个决定一行：问题 → 默认值（标「猜的」）｜猜错的代价。发出前可改；执行者按默认走，不停下来等。

写不出机器可判命令的目标（文风、体验类）也记在这里：改成抽查点＋用户亲验，注明这活只能半托。

## 界限

- 白名单：只允许改哪些路径＋新建文件，其余只读——用白名单不用黑名单，黑名单永远列不全
- 判卷标准（测试、验收脚本、CI 配置）碰都不许碰；无 git 时给每个文件的 sha256 指纹（文件内容的数字摘要，交付时必须一字不差）
- 点名最诱人的顺手活（那个一行就能修的 bug、顺手重构、顺手装工具），写明进 `BLOCKED.md` 待裁决；收不回的操作（删数据、改权限）停下写 `BLOCKED.md` 做别的

## 现状与任务 0

- 实测数字逐条带来源与日期，查不到的标「猜的，没验证」；能提前实证的关键结论（如「只改实现就能全绿」）写进来，提前拆掉借口
- 任务 0：跑指定命令核对上面的数字，不存在的命令、空转的假检查当场记 `BLOCKED.md`；对不上就停，证据写 `BLOCKED.md` 最上面，只做不受影响的部分；核对无误后把「理解的目标／顺序／最大风险」≤10 行写进 `PROGRESS.md` 再动工

## 任务 N

每个任务包含：一句话目标带数字；从哪下手一句（多任务按依赖排序，说清为什么它排前面）；死规矩写成「做 A，否则 B」并带具体后果；验收＝命令＋机器可判的判定（含防漏判定，如「跳过 0」）；反向验证＝故意制造一次失败、贴变红输出、还原后贴全绿——凡是「坏了没人会知道」的检查都要这一步。

## 规矩

- 防作弊点名到具体姿势：跳过测试（skip/todo）、放宽判断、把被测对象换成假的（mock）、删测试、改阈值或验收脚本、`|| true`（失败也当成功）——全算失败；测试数／覆盖率只许 ≥ 基线；补测试类任务加「实现目录 `git diff` 为空（业务代码一行没动）」
- 不新增流程、权限、依赖，必须加的写 `BLOCKED.md`
- 同一条验收连败 3 次换下一项；结果比开工差就回滚如实报告——「没做成但说清了」合格，「做了但更糟」不合格
- 项目自有纪律（分支／PR 规则、提交前检查）写在这里

## 完成条件

- 两条硬指标：一条度量要的结果（不是工作量），一条守约束（指纹没变、回滚＝0 之类）
- 一句「每条都要在对话里贴实际命令输出（含反向验证的红→绿证据），只说做完了不算」——判完成的小模型不跑命令、不读文件，只认对话里贴出的内容
- `BLOCKED.md` 随交付提交，空的也写「无」
- 止损：「或已跑满 N 轮——满轮即停，如实汇报卡在哪、还差什么」

## 探索型：改四处，其余同款

用户要的是答案本身（调研、选型、「该不该做 X」）时，硬指标只会换来凑数的答案。判定方式：**动笔前写不出一条能机器判定的验收命令，就是探索型。**

| 改哪节 | 执行型 | 探索型换成 |
|---|---|---|
| 完成条件 | 两条硬指标 | 学习目标：结论条数设上限、每条附来源与日期或可复跑的复现步骤——宁收 2 条实的，不收 10 条凑的 |
| 止损 | 验收连败 3 次换项 | 可承受损失：最多烧多少时间／查多少来源，烧完就交卷，交「目前最优＋还没排除什么」 |
| 防作弊 | 主防让检查变绿 | 主防编造：凑数的结论、查无此文的引用、没跑过的「实测」都算作弊；每条结论要经得起随机抽一条、10 分钟内复现 |
| 失败定义 | 没达标＝不合格 | 此路不通＝合格交付：带证据证明某方向是死路（死因＋原始输出），按完成计 |

其余各节（开头五件事、拍板记录、界限、任务 0、`PROGRESS.md`／`BLOCKED.md` 机制）照执行型原样写。

## 循环型：改四处，其余同款

这活会被重复触发（每周一遍、每次发版、每来一个新 issue）时，一次性的书跑完就作废，下次连人带 agent 重来一遍——反复发生本身就是它值得被规格化、被交出去的理由。判定方式：**问一句「同一套输入源和产出，下次还会原样再来一遍吗」，答会就是循环型。**「这类活以后还会有」不算——补一批遗留测试、做一次迁移、清一次历史债都属于干完就没了的一次性活，走执行型。

| 改哪节 | 执行型 | 循环型换成 |
|---|---|---|
| 完成条件 | 两条硬指标 | 加一条可重复性：不只这次跑通，同一条命令第二次跑仍通——验收要贴出第二次运行的输出。只跑通一次的往往是撞对了一次性状态（缓存在、端口空着、那个文件刚好还在） |
| 交付物 | 改动＋验收输出 | 加「下次靠什么再跑」：脚本、cron／launchd 条目、或一份写清触发与步骤的规格文件，路径写进完成条件。留不下这个就等于没自动化，只是这次替人干了一遍 |
| 现状与任务 0 | 核对基线数字 | 加核对触发源：那个「事件」现在真能被看见吗（文件真会出现、接口真有这个字段、日志真会打这行）。触发源摸不到，整套自动化每次都空跑或漏跑，这是循环型的头号死法 |
| 防作弊 | 主防让检查变绿 | 加主防写死一次性状态：把当次的日期、目录名、id 硬编码进脚本，这次全绿下次全错。判据是「换一天、换一个输入还成立吗」 |

其余各节（开头五件事、拍板记录、界限、`PROGRESS.md`／`BLOCKED.md` 机制）照执行型原样写。

- 触发方式和人工关口在 Step 2 问清（事件触发还是定时；哪步要人点头还是全程不用人管），答案写进「我替你拍的板」。这两件决定交付物长什么样，猜错要重写。
- 不必凑齐结构：一条 cron 加一个脚本就能解决的循环，不要因为这是 goal-plan 就硬套一份 agent 任务书——那是给一件确定的事引入不确定性。这时交付「脚本＋一句怎么装上」比交任务书更对。

## 一份书只装一型

同时像两型的（既要答案也要落地、既是循环又要先出结论）拆成两件：先出结论那件按探索型写，用户看过结论再据此写第二件。「查清哪些能自动化，然后自动化」就是这个形状——先探索型摸清哪些值得自动化，再据此写循环型的书。不许一份书混两型，混了验收标准会自相矛盾：探索型收「宁收 2 条实的」，执行型和循环型收硬指标，两套判据同时在场，执行者会挑对自己有利的那套交卷。
