# Claude Code 协作效率复盘

用历史会话记录回答三个问题：

1. 哪些行为反复出现？
2. 哪些信号有充分证据，哪些只是待核验线索？
3. 先改哪一两件事最实际？

## 数据边界

扫描结果是启发式指标，不是完整事实。报告必须主动说明以下限制：

- `session_span_h` 是会话首条到末条记录的墙钟跨度，包含用户离开、等待和挂机时间，不能称为“工作时长”“协作小时”或“实际损耗”。
- “用户纠正”来自关键词匹配。必须抽样查看 `correction_examples`，不能把命中数直接当成真实返工数。
- “连续探索”只表示连续多个单工具轮次。后一步可能依赖前一步结果，不能一概写成“本可并行”。
- “重复读取”可能来自文件被修改、上下文压缩或合理复查。没有会话上下文时只能称为候选问题。
- “完成后缺少验证信号”表示附近记录中没有识别到测试命令，不等于一定没有验证。
- `fail_buckets` 按错误文本签名分桶，一条失败只进一个桶。`F1` 里多数是一次调用串多段命令、末环非零导致整条标红，错误正文往往已经带到有效输出，不能按条数当成等量损耗。
- 相关性不是因果。除非日志能直接串起事件顺序，否则使用“可能相关”“值得检查”，不要写“根因就是”。

## 参数

用户已经给出范围时直接执行，不重复提问。缺少信息时只问会改变结果的问题；其余使用默认值：

- 数据源：Claude Code 会话日志
- 时间窗：最近 30 天
- 范围：全部项目
- 输出：主要发现、典型证据、可执行建议

若用户明确要求单项目，使用 `--cwd-filter`。非 Claude 会话日志的分析不属于本 Skill。

## 执行流程

### 1. 扫描日志

```bash
python3 ~/.claude/skills/loss-analysis/scripts/scan.py \
  --days 30 \
  --output /tmp/claude-loss-analysis/raw.json
```

先读 stdout 摘要，它已带上 `fail_buckets_top6`、`retry_after_fail` 和 `monthly_fail_rate_pct`，多数结论不用再打开 JSON。需要样本时读 `raw.json` 的 `fail_bucket_examples`（每桶 3 条）。

不要把整批 JSONL 日志读入上下文，也不要另写临时脚本重新扫一遍——失败分桶、按月归一化和失败后重试判定都已经在 `scan.py` 里。这三样以前靠现场写脚本补，一次要多花十几轮调用。

### 2. 核验高位信号

生成结论前至少完成这些检查：

- 抽样查看纠正、未验证各 3-5 条；明显误报要从结论中剔除。
- 工具失败不要抽样，直接看 `fail_buckets`。归因前先扣掉两类：`A*` 是门禁和环境限制在正常工作，`E*` 是检索无匹配这种正常语义的非零退出。剩下的 `B*` `C*` `D*` `F1` 才可能是可避免的。
- 要不要为某一类提建议，看 `monthly[].buckets_per_1k_calls` 的趋势，不看绝对数。绝对数最大的那类可能正在自行收敛，给它加规则只是往下降曲线上叠维护成本。窗口内最后一个月天数不足时，它的趋势只能当补充证据。
- 失败数不等于返工数。看 `retry_after_fail`：`moved_on` 是探到边界就换方向，不是返工；只有 `retry_near_identical` 是原样重试的真返工。两者实测差约 6 倍，直接把失败数说成损耗会高估一个数量级。
- 对排名靠前的连续探索和重复读取，至少检查一个原会话，判断是否有顺序依赖、文件改动或压缩。
- 数字与样本冲突时，以样本核验后的结论为准，并说明规则为什么误报。
- 没有事件级耗时数据时，按证据强度和影响范围排序，不按虚构的“损耗小时”排序。

### 3. 生成报告

以 `assets/report-template.html` 为骨架，替换占位符并删除未使用的模块。允许调整章节数量和内容长度；不要为了填满模板重复结论。

默认结构：

1. **结论**：三句话以内，先说最重要的发现。
2. **数据口径**：时间窗、样本量、已知限制。
3. **主要发现**：每项只写“结论 / 证据 / 建议 / 限制”中确实需要的部分。
4. **建议**：最多三项，按预期收益、实施成本和证据可信度排序。

### 4. 写文件并预览

输出到：

```text
~/Documents/md/YYYY-MM-DD-claude-task-loss-analysis.html
```

macOS 用 `open` 预览。最终回执只包含报告路径、最重要的两项发现和原始 JSON 路径，不复述报告全文。

## 中文表达要求

报告写给正在做事的人，不写成咨询报告或模型自我表演：

- 一句话只表达一个主要意思，优先使用短句和常用词。
- 先说发生了什么，再给数字和样本，最后给建议。
- 能写“最值得先改”时，不写“最高杠杆”；能写“主要项目”时，不写“主战场”。
- 避免“水下损耗、出血点、打法、抓手、方案骨架、被打回、双管齐下、证伪”等夸张或生硬词。
- 不用“宏观信号、综合诊断、深层根因”包装普通统计。
- 不替用户下情绪判断，不把低频问题写成严重失误。
- 引用用户原话时保持原文；分析正文使用自然、克制的简体中文。
- 每个判断都区分：**直接测量**、**规则命中**、**分析推断**。

## 质量检查

交付前确认：

- 所有数字都能在 `raw.json` 找到。
- 没把会话跨度写成实际工作时长。
- 没把启发式命中写成确定事实。
- 没有模板占位符残留。
- HTML 可直接打开，长文本和表格没有溢出。
- 结论与建议没有重复三遍。
