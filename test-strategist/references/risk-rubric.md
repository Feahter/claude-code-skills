# 风险分级 rubric

分级分两步：**先由失效后果定基线，再由有证据的四维调整**。不做 1–100 打分，也不做「严重度 × 发生率 × 可检测度」的乘积——那种数字看着精确，实际是把三个拍脑袋的数乘在一起，误差相乘而非相消。

## 第一步：后果基线

看「这个失效真发生了，最坏会怎样」。取最坏合理情形，不取最坏想象情形。

| 级别 | 后果特征 | 例 |
|---|---|---|
| **P0** | 不可逆资金损失；权限越界（能读写他人数据）；数据完整性破坏（丢数据、脏数据、对不上账）；核心链路大范围不可用；合规违规 | 重复扣款、越权查看他人订单、迁移丢字段、支付全线不可用 |
| **P1** | 可逆但打到核心链路；单用户数据错误但可修复；主要功能不可用且无好的绕行 | 下单失败率上升、订单状态卡住需人工改、优惠算错但能退补 |
| **P2** | 体验明显受损；非核心功能异常；有可接受的绕行方案 | 列表排序错、导出偶发失败可重试、提示文案误导 |
| **P3** | 边缘场景、纯展示、内部工具小瑕疵 | 极端窗口宽度下错位、非关键页面文案 |

**P0 是白名单制**：不属于上表 P0 那五类的，无论听起来多严重，都不许升 P0。「用户会很生气」不是 P0 依据。

## 第二步：四维调整

四维**只能各调 ±1 级，累计最多 ±1 级**，且每一维的调整必须附证据。拿不出证据的维度按「中性」处理，不参与调整。

| 维度 | 往上调的条件 | 往下调的条件 | 证据怎么取 |
|---|---|---|---|
| **影响面** | 核心链路 / 全量用户 / 主要收入路径 | 灰度中 / 内部工具 / 极少数用户 | 路由与入口位置、埋点或流量数据、调用方数量（`trace_path` 查 inbound）、是否在 feature flag 后面 |
| **变更频度** | 这块近期反复改动，改动集中 | 长期稳定未动 | `git log --oneline -20 -- <path>` 看近期提交密度；`git log --since` 数窗口内次数 |
| **历史高发** | 这块出过事故 / 有过 hotfix / 有反复回归的 issue | 从未出过问题且有测试守着 | 事故记录、`git log --grep='hotfix\|revert\|fix' -- <path>`、issue 追踪 |
| **可逆性** | 出错难以察觉或难以回退 | 有开关能秒关、数据可重算、有幂等补偿 | 有无 feature flag、有无回滚脚本、数据是否可从上游重放 |

**不可逆性是例外**：如果失效直接导致不可逆后果（钱出去了、数据删了、消息发出去了），不走调整项，直接按 P0 基线判。

## 第三步：证据强度封顶

分级不能超过证据能支撑的程度。

| 证据强度 | 定义 | 优先级上限 |
|---|---|---|
| **强** | 读到了具体代码 / diff / 日志 / 事故报告，能给出 `file:line` 或记录编号 | 无上限 |
| **中** | 有间接证据（相邻代码的模式、同类模块的历史问题、需求文字明确写了这个约束） | 最高 P1 |
| **弱 / 无** | 只有通用经验、行业常识、类比推测（`assumption-no-evidence`） | 最高 P2 |

这条封顶规则是硬的。它防的是最常见的失真：**用专业术语把猜测包装成 P0**。一份策略包里如果 P0 全靠 `assumption-no-evidence`，说明这次分析没做，只是背了一遍风险清单。

## 排序规则

同级内按下面顺序排，先到先测：

1. 不可逆的排在可逆的前面
2. 无监控兜底的排在有监控的前面（出了看不见比出了能看见更危险）
3. 证据强的排在证据弱的前面（先干确定的活）
4. 落地成本低的排在成本高的前面（同等风险下先拿容易的）

## 处置选择

分完级要选处置（铁律 2 的五选一），选择依据不是「重不重要」而是「什么手段最适合这个风险」：

| 风险特征 | 建议处置 |
|---|---|
| 触发条件明确、结果可判定、能稳定复现 | `test` |
| 触发条件依赖真实流量 / 时序 / 规模，测试环境造不出 | `monitor` |
| 根子在设计上，加测试只是给病灶盖被子 | `design-fix` |
| 需要人的直觉与实时判断，脚本化收益低 | `explore` |
| 成本明显高于风险敞口，或已有其他层兜住 | `accept`（**必须记录决策人**） |

组合是允许的（`test-and-monitor` 最常见：测试防回归，监控防没想到的路径）。

**不许出现的处置**：「后续跟进」「加强关注」「视情况而定」——这些不是处置，是把决定往后推。真要推就写 `accept` 并注明重新评估的触发条件。
