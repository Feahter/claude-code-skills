# 失效模式：并发、幂等与时序

适用：并发写、重试、锁、分布式协调、定时任务、任何「同一件事可能被做两次」的变更。

这一类的共同特征：**串行测试全绿，上线才炸**。所以它的验证义务经常不是「写个测试」，而是「加唯一约束 + 加监控」。

## 失效模式清单

### 竞态

- **先查后写（check-then-act）**：`SELECT 不存在 → INSERT`，并发下两个请求都通过检查
- **读改写丢失更新**：A、B 都读到余额 100，各自减 30，最终是 70 而不是 40
- **ABA**：读到的值中途被改成别的又改回来，看起来没变，实际中间状态已被消费
- **状态机并发跃迁**：两个请求同时推进状态，`待支付 → 已支付` 和 `待支付 → 已取消` 同时成功
- **初始化竞态**：多个请求同时触发懒初始化，创建出两份资源

### 幂等

- **无幂等键**：写接口靠「客户端不会重复调」这个假设
- **幂等键作用域错**：按用户维度做键，同一用户的两笔不同业务被误判为重复
- **幂等窗口太短**：幂等记录 5 分钟过期，但客户端重试窗口是 1 小时
- **幂等只挡住入口没挡住副作用**：接口返回了「重复请求」，但消息已经发出去第二次
- **返回值不幂等**：重复请求被正确拦截，但返回体与首次不同，客户端走错分支

### 重试

- **重试非幂等操作**：把「扣款」重试成两次扣款
- **无退避的重试放大**：下游抖动 → 所有客户端同时重试 → 下游彻底压垮
- **超时与重试叠加**：客户端超时重试，服务端其实两次都执行成功
- **重试次数与总耗时失控**：三层各重试 3 次 = 27 次请求
- **重试掩盖真实错误**：最终成功了，但没人知道失败过（无可观测信号）

### 锁

- **锁粒度过粗**：全局锁把不相关的操作串起来，性能塌陷
- **锁粒度过细**：多个锁 → 死锁（获取顺序不一致）
- **分布式锁失效**：持有者 GC / 网络分区导致锁过期，两个持有者并存
- **误释放他人锁**：释放时不校验持有者标识
- **锁续期缺失**：业务耗时超过锁 TTL
- **锁与事务边界错位**：锁在事务外获取释放，事务提交前锁已放

### 顺序与时钟

- **消息 / 事件乱序**：后发的先到，状态被旧事件覆盖
- **依赖时钟单调**：用 `Date.now()` 做排序或超时判断，遇到时钟回退（NTP 校正）
- **跨节点时间不一致**：用各自本地时间比较先后
- **定时任务重入**：上一轮没跑完下一轮又起（多实例部署下更明显）
- **定时任务多实例重复执行**：没有选主或分布式锁

### 资源竞争

- 连接池 / 线程池耗尽导致的级联超时
- 限流误伤（同一 IP 的正常批量被当攻击）
- 慢请求占满资源，快请求也排队

## 常用 oracle

并发类风险的 oracle 有一个共同形态：**并发执行 N 次，某个量必须等于 1 或保持守恒**。

| 风险类型 | oracle 取向 |
|---|---|
| 先查后写 / 重复创建 | **副作用计数**：并发 N 次，落库记录数 == 1，其余请求收到明确的重复响应 |
| 丢失更新 | **守恒**：N 个并发各减 1，最终值 == 初始值 − N |
| 幂等 | **副作用计数 + 返回一致**：同键请求 N 次，副作用一次，且 N 次返回体相同 |
| 状态机并发 | **状态转换合法性**：并发推进后状态是合法终态之一，且不存在两个互斥终态同时成立的痕迹 |
| 库存 / 余额 | **不变量**：任何时刻不为负（这条要在并发压力下验，不是单请求验） |
| 重试放大 | **单调性 / 边界**：总请求数 ≤ 配置上限；有退避（间隔递增） |
| 死锁 | **必须完成**：并发混合顺序操作在超时内全部完成，无一挂起 |
| 定时任务重入 | **副作用计数**：一个调度周期内业务副作用发生 1 次 |
| 时钟 | **单调性**：时间戳序列不回退；超时判断不依赖墙上时钟差 |

## 证据来源

| 要找什么 | 去哪找 |
|---|---|
| 幂等实现 | 幂等键表 / Redis key、唯一索引（**唯一约束是最后防线，有没有它决定风险等级**） |
| 锁实现 | 分布式锁封装、`SELECT ... FOR UPDATE`、乐观锁版本号字段 |
| 重试配置 | HTTP 客户端 retry 配置、MQ 消费重试次数、退避策略参数 |
| 事务与锁的相对位置 | 事务注解与加锁调用在调用链中的顺序 |
| 定时任务 | cron 配置、调度框架配置、是否有选主 / 分布式锁 |
| 部署形态 | 实例数（多实例是很多并发问题的前提条件，单实例时这些风险不成立） |
| 时钟依赖 | grep `Date.now()` / `new Date()` 参与比较或排序的地方 |

**判定捷径**：先看有没有唯一约束 / 幂等键。有 → 竞态风险从 P0 降到 P1（数据库会兜住，最坏是报错）。没有 → 保持 P0，且处置至少是 `design-fix`（补约束）而不是只 `test`。

## 可测试性阻塞信号

- **测试框架串行执行，造不出真并发** → 竞态类义务无法用常规测试验证。处置改为 `design-fix`（加唯一约束，让数据库保证）+ `monitor`（观测重复率），并在不覆盖范围里写明「并发路径未经测试验证」
- **无法控制执行时序**（没有可注入的暂停点）→ ABA、丢失更新这类需要精确交错的场景测不出，标 `testability_gap`
- **单实例测试环境** → 分布式锁、定时任务重复执行类风险结论不可迁移，必须显式声明
- **时钟不可控** → 时钟回退、TTL 过期类场景无法验证，需要可注入的时间源（`design-fix`）
- **无法观测副作用次数** → 所有「计数型 oracle」失效，先补可观测出口

**这一类最诚实的结论常常是「测不了」**。写清楚测不了、为什么、改成什么处置，比硬造一个串行的假并发测试有价值——后者会给出虚假的安全感，而虚假的安全感比没有测试更危险。
