# 失效模式：缓存与消息

适用：缓存读写、消息队列、异步任务、事件驱动链路的变更。

## 缓存失效模式

### 一致性

- **更新顺序错**：先更库后删缓存，两步之间的读请求把旧值又写回缓存（经典的双写不一致）
- **删缓存失败无补偿**：更新库成功、删缓存失败，脏数据留到 TTL 到期
- **本地缓存多实例不一致**：实例 A 更新了自己的本地缓存，B 的还是旧的
- **缓存重建竞态**：多个请求同时发现未命中，同时回源并各自写入（可能写入不同版本）
- **写缓存不写库**：只更新缓存，重启即丢

### key 与隔离

- **key 冲突 / 未隔离**：多租户或多环境共用 key 前缀，读到别人的数据（这是数据泄露，按 P0 判）
- **key 未包含全部变量**：按用户查询的结果缓存在不含用户 id 的 key 上
- **key 未随版本变化**：数据结构改了，key 没变，读到旧结构

### 序列化与结构

- **序列化格式变更**：新代码读不了老缓存的字节，反序列化抛异常
- **字段增删**：新增必填字段，老缓存里没有，读出来是 undefined 并被当合法值使用

### 容量与失效

- **穿透**：查不存在的 key 每次都打到库（无空值缓存）
- **击穿**：热 key 过期瞬间大量请求同时回源
- **雪崩**：大批 key 同一时刻过期（TTL 都设成固定值，没加随机抖动）
- **TTL 与业务窗口不匹配**：权限缓存 30 分钟，但权限收回要求立即生效
- **淘汰导致的行为变化**：内存满触发淘汰，被当作缓存击穿的偶发故障

## 消息失效模式

### 投递语义

- **重复投递**：绝大多数 MQ 是 at-least-once，**消费端无幂等就是缺陷**，不是风险
- **消息丢失**：生产端未确认发送成功就返回；未开持久化；消费端先 ack 后处理，处理失败消息已丢
- **乱序**：并发消费打乱顺序，旧状态覆盖新状态
- **事务消息不一致**：本地事务回滚了但消息已发出（或反之），最典型的分布式一致性缺口

### 消费端

- **消费失败无限重试**：一条毒消息卡死整个分区
- **死信队列无人看**：进了死信等于数据静默丢失
- **消费幂等键选错**：用 messageId 做幂等，但重投时 messageId 变了
- **消息格式不兼容**：生产端先上线发新格式，消费端还是老代码
- **积压**：消费速度跟不上，延迟从秒级涨到小时级，下游业务按「实时」假设写的逻辑失效
- **并发消费与顺序要求冲突**：为了提速开并发，破坏了同一实体的顺序保证

### 链路

- **异步任务执行结果无人知道**：失败了没有任何信号
- **重放不安全**：为了修数据重放历史消息，副作用被重复执行
- **上下游耦合了消息体全部字段**：加字段就炸

## 常用 oracle

| 风险类型 | oracle 取向 |
|---|---|
| 缓存一致性 | **往返**：更新后立刻读，拿到新值；等待 TTL 内不出现旧值 |
| 缓存 key 隔离 | **必须失败 / 不可见**：租户 A 的操作后，租户 B 读到的仍是自己的数据 |
| 序列化兼容 | **参照对照**：用老格式的缓存字节喂给新代码，不抛异常且字段语义正确 |
| 穿透 / 击穿 | **单调性 / 边界**：N 个并发未命中请求，回源次数 ≤ 1（或 ≤ 阈值） |
| 重复投递 | **副作用计数**：同一消息投递 N 次，业务副作用发生 1 次 |
| 消息不丢 | **守恒**：发送 N 条，成功消费 + 死信 == N |
| 乱序 | **状态转换合法性**：乱序投递后终态正确，或旧事件被显式丢弃并留痕 |
| 事务消息 | **不变量**：本地事务回滚的场景下，消费端不产生任何副作用 |
| 死信可观测 | **可观测信号**：消息进死信时有告警信号可断言，不是靠人去翻队列 |
| 积压 | **边界**：端到端延迟 P95 < 阈值（阈值要有业务来源） |

## 证据来源

| 要找什么 | 去哪找 |
|---|---|
| 缓存读写顺序 | 缓存封装层的 update / invalidate 方法，看它与 DB 写的相对位置 |
| TTL 与抖动 | 缓存配置常量、是否有随机化 |
| key 构造 | key 生成函数（**重点看有没有把租户 / 用户 / 版本纳入**） |
| 序列化 | 序列化器配置、缓存值的结构定义与其变更历史 |
| 消费幂等 | 消费者入口的幂等判断、幂等键来源 |
| ack 时机 | 消费者是自动 ack 还是手动，手动 ack 在处理前还是处理后 |
| 死信与重试 | MQ 配置（重试次数、死信队列、TTL）、死信有没有告警 |
| 消息契约 | 消息体的结构定义 + `git log` 看字段变更 |
| 上下游 | codebase-memory `trace_path` cross_service 模式查 Channel 节点，找生产者与消费者 |

**判定捷径**：消费端有没有幂等判断，以及 ack 在处理前还是处理后。这两个位置决定了「重复」和「丢失」两类风险的等级，读两个文件就能定。

## 可测试性阻塞信号

- **无法构造重复投递 / 乱序** → 幂等与顺序类义务改为 `design-fix`（补幂等键）+ `monitor`（观测重复处理次数）
- **测试环境缓存与生产共用** → 任何缓存隔离结论不可信，且测试本身可能污染生产，先解决隔离
- **无法观测回源次数 / 消费次数** → 计数型 oracle 全部失效，先补可观测出口
- **死信无查询接口** → 「不丢」类 oracle 中的死信项无法统计，守恒式判据不可用
- **消息延迟不可测量** → 积压类风险只能 `monitor`

异步等待在测试里怎么写（禁死等待、怎么轮询到条件成立）归 `playbook/references/assertions.md`；mock MQ 与缓存的方案归 `playbook/references/mocking.md`。
