# Oracle 模式：怎么写得出「怎么算通过」

Oracle 是**判据**——拿什么来断定这次行为是对的。它是策略包里最容易糊过去、也最不能糊过去的字段。

为什么最不能糊：一份 115 篇文献的系统综述（arXiv 2511.21382）结论是，LLM 生成的测试最大的通病是 **weak fault detection**——能编译、能跑、覆盖率好看，但抓不到真 bug。抓不到的直接原因就是 oracle 太弱：断言只验了「没崩」，没验「结果对」。Meta 的 ACH 工具解决这个问题的入口，正是让人先用纯文本把「要防的故障长什么样」说清楚，再倒推出能抓住它的判据。

所以本 skill 的 `failure_mode` + `oracle` 两个字段是配对的：**先说清 bug 长什么样，再写出能抓住它的判据**。

## 合格线

一个 oracle 合格，要同时满足：

1. **可判定**——给定一次执行，能机械地判出真假，不需要人再想一想。
2. **与 failure_mode 对应**——这个 bug 真发生时，这个判据一定为假。反过来说：如果 bug 发生了判据还是真，这个 oracle 是废的。
3. **不重述实现**——判的是外部可观察的结果，不是「代码有没有走到那一行」。

自检一句话：**把 failure_mode 描述的 bug 手工植入代码，这条 oracle 会不会变红？**答不出来，说明 oracle 还没想清楚。

## 模式清单

按适用场景挑，一条风险常常需要两条 oracle 组合（一条管结果、一条管副作用）。

| 模式 | 判什么 | 例 |
|---|---|---|
| **不变量** | 无论怎么操作都必须恒成立的性质 | 账户余额 = 初始余额 + Σ入账 − Σ出账；库存 ≥ 0 |
| **守恒 / 对账** | 转移前后总量不变 | 转账后 A+B 总额不变；出入库流水合计 = 库存变化 |
| **副作用计数** | 关键副作用发生的**次数** | `refund_transaction_count == 1`；短信只发一条；MQ 只投递一次 |
| **状态转换合法性** | 状态机只能按允许的边走 | 订单不能从 `已取消` 变回 `待支付`；非法转换必须被拒绝并留痕 |
| **往返（round-trip）** | 编码后解码 / 写入后读出 应等于原值 | 序列化再反序列化相等；保存后重新加载表单值不变 |
| **参照对照** | 与另一套可信实现或历史版本比对 | 新算法结果与旧算法在同一批输入上一致；与后端返回值比对前端计算 |
| **变形关系（metamorphic）** | 输入按某种方式变化，输出应有可预测的对应变化 | 搜索词加空格结果不变；金额单位换算后总额等价；列表逆序后取反仍是同一集合 |
| **必须失败** | 非法输入 / 越权操作**必须被拒绝**，且拒绝方式正确 | guest 请求 admin 接口返回 403 而非 200 空数据；超额提现被拒且不产生流水 |
| **单调性 / 边界** | 应当单调或有界的量不越界 | 重试次数不超过上限；分页 offset 不越界；时间戳不回退 |
| **可观测信号** | 关键路径留下可断言的痕迹 | 幂等键写入日志；关键决策打了埋点，事后能对账 |

## 反例清单

这些一律不合格，写进策略包会被 `scripts/validate-package.sh` 拦掉：

| 反例 | 为什么不行 | 改成 |
|---|---|---|
| 「验证功能正常」 | 判不了 | 说清哪个可观察量等于什么 |
| 「页面正常显示」 | 判不了；且「显示」不等于「数据对」 | 「订单金额显示 ¥99.00，与接口返回 amount 一致」 |
| 「不报错」 | 最弱的 oracle。静默错误（算错但不抛）全漏 | 加结果判据，别只判异常 |
| 「接口返回 200」 | 200 + 错误 body 是常见故障形态 | 200 且 body 满足具体结构与值约束 |
| 「覆盖率达到 80%」 | 覆盖率是过程指标，不是判据 | 换成具体行为判据 |
| 「与预期一致」 | 「预期」没写出来 | 把预期值写出来 |
| 「响应时间可接受」 | 没有阈值 | P95 < 300ms（阈值要有来源） |

## 非确定性输出怎么写 oracle

AI / LLM 功能、涉及随机或时间的功能，输出不固定，不能用等值断言。可用的三条路：

1. **属性断言**：不判具体输出，判输出必须满足的性质（格式合法、必含字段、长度区间、不含敏感词、引用的 id 在库内存在）。
2. **变形关系**：同义改写输入，结果的关键结论应不变；无关信息加进输入，结论不应翻转。
3. **参照评估**：用固定评估集 + 打分器，判**分数不低于基线**而非判逐条相等。基线要版本化，回归时对比。

细节见 `failure-modes-ai.md`。要点是：**非确定性不是「没法验」的借口**，只是不能用等值断言。

## 与 playbook 的分界

本卡只管**判据的内容**（判什么、判到什么程度）。判据用什么 API 落地——`expect(locator).toBeVisible()` 还是 `toHaveText`、要不要 web-first 断言、双模态断言怎么写——全部归 `playbook/references/assertions.md`，**这里不写一行断言代码**。

一句话：这里定「必须证明退款只发生一次」，playbook 定「这句断言在 Playwright 里怎么写才不 flaky」。
