# 右移：事故根因与系统性预防

适用：线上事故、故障报告、客诉、逃逸缺陷（测试没抓到但用户遇到了的）。

这个场景的价值不在于修好这一个，在于**回答「同样的病还在哪」**。只修当前这一处，下次换个模块再来一遍。

## 五步流程

### 1. 分离现象与原因

先把事实钉住，不许跳到结论：

- **现象**：用户看到什么 / 监控报了什么 / 影响范围与时长
- **触发条件**：什么输入或什么状态下发生，能不能复现
- **直接原因**：哪一行代码 / 哪个配置导致了这个现象（要有 `file:line` 或配置项）

复现不了的要写明「未能复现」，不要把猜测写成直接原因。

### 2. 根因分类

用固定分类，不要自由发挥。**分类决定了预防措施该往哪走**：

| 根因类别 | 特征 | 预防方向 |
|---|---|---|
| **逻辑缺陷** | 条件写错、边界差一、分支遗漏 | 补测试（这类最适合测试防回归） |
| **并发与时序** | 串行没问题，并发才出 | 加约束（唯一索引 / 锁）+ 监控；测试往往测不出 |
| **契约不一致** | 前后端 / 服务间对字段语义理解不同 | 契约测试 + 类型共享 |
| **配置与环境** | 代码没问题，配置错或环境不一致 | 配置校验 + 环境一致性检查（测试通常无能为力） |
| **依赖故障** | 下游挂了 / 慢了，本服务没兜住 | 超时、降级、熔断 + 混沌验证 |
| **数据形态意外** | 生产有测试没见过的脏数据 / 极端数据 | 从生产脱敏取样进测试数据集 |
| **设计缺陷** | 这个失败在当前设计下必然可能发生 | `design-fix`。加测试只是给病灶盖被子 |
| **流程缺失** | 没评审 / 没测 / 没监控 / 没灰度 | 改流程，不是加测试 |
| **认知缺失** | 团队不知道这个约束存在 | 写进文档 / 检查清单 / 本 skill 的方法卡 |

**关键判断**：如果根因是「设计缺陷」或「流程缺失」，那么补测试是错的处置——测试会一直绿，问题会换个形式再来。

### 3. 同类风险扫描（这一步最有价值，也最常被跳过）

拿着根因去问：**这个模式还在哪里**。

```bash
# 例：根因是"金额用了浮点"
grep -rn 'float\|double' --include='*.ts' | grep -i 'amount\|price\|fee\|balance'

# 例：根因是"先查后写无唯一约束"
# 找所有 "先 findOne 再 create" 的模式（ast-grep 比 grep 准）
# 再逐个核对对应表有没有唯一索引

# 例：根因是"消费端无幂等"
# codebase-memory: 查所有 Channel 消费者节点，逐个看入口有没有幂等判断
```

每找到一处同类，就是一条新风险，走标准分级与处置。**这是从「修一个 bug」变成「消除一类 bug」的唯一路径**，也是 mind.md 里「系统性预防」落地的具体动作。

扫不动的时候（模式太抽象、代码库太大）要写明扫描范围和方法，说清「我扫了哪些、没扫哪些」，不要给出「已全面排查」这种无法核实的结论。

### 4. 分配预防措施

一次事故通常需要多种措施配合，按下表分配，不要全压在测试上：

| 措施 | 解决什么 | 对应处置 |
|---|---|---|
| 补回归测试 | 防这一个 bug 再来 | `test` |
| 补监控 / 告警 | 下次早发现（尤其是测不出来的那类） | `monitor` |
| 加数据库约束 | 让错误状态在存储层不可能存在 | `design-fix` |
| 改设计 | 消除失败的可能性而不是检测它 | `design-fix` |
| 改流程 / 加检查清单 | 防同类问题重新进入 | 流程项，记录负责人 |
| 补文档 / 方法卡 | 消除认知缺失 | 可直接更新本 skill 的对应方法卡 |

**回归测试的 oracle 必须能抓住原始 bug**：把修复回滚掉，这条测试必须变红。做不到这一点，这条测试是装饰品。这是本 skill 里唯一强制「验证测试有效性」的地方，因为这里有现成的故障样本，验证成本几乎为零。

### 5. 产物

标准策略包 + 三样额外内容：

- **事故档案**：现象 / 触发条件 / 直接原因 / 根因分类 / 影响范围与时长
- **同类风险清单**：扫到的每一处 + 位置 + 分级 + 处置（这是主要交付物）
- **预防措施表**：每条措施 + 类型 + 负责方 + 验证方式

## 反模式

| 反模式 | 为什么不行 | 改成 |
|---|---|---|
| 根因写成「开发疏忽」「测试遗漏」 | 指向人不指向系统，无法预防 | 问「什么样的系统设计让这个疏忽能上线」 |
| 只补一条测试就宣布闭环 | 同类问题还在别处 | 必须做第 3 步同类扫描 |
| 5 Whys 追到「因为公司没有质量文化」 | 追过头，落不到可执行动作 | 停在「能被一个具体动作解决」的那一层 |
| 5 Whys 只追一层就停 | 追不够，修的是症状 | 至少追到根因分类表里能对上一类 |
| 把所有措施都设成「补测试」 | 配置类、并发类、设计类根因，测试大多无效 | 按第 4 步的映射表分配 |
| 回归测试不验有效性 | 可能加了个永远绿的测试 | 回滚修复看它是否变红 |
| 「已全面排查，无同类问题」 | 无法核实，通常也不是真的 | 写清扫描范围与方法，列出未覆盖部分 |
