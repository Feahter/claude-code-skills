# 自动化测试环节完整性

适用：已有测试套件，但要判断「这套东西作为一个体系，缺了哪个环节」。典型触发是「测试写了不少，线上还是出问题」。

七个环节，逐个查缺口。**每个缺口都要落成验证义务或 `design-fix`，不是罗列现状**。

## 1. 数据准备

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 用 UI 点几十步造数据 | 慢且脆，一个前置页面改动全套挂 | 改用 API / 直连 DB 造数（实现归 playbook） |
| 测试间共享数据 | 单跑过、批量挂；顺序依赖 | 每用例独立数据 |
| 无清理机制 | 数据累积，跑久了行为变化 | 用后即弃或每轮重置 |
| 造不出异常形态数据 | 边界与脏数据场景测不了 | 从生产脱敏取样，补进数据集 |
| 造数依赖人工准备 | 无法进 CI | 造数脚本化 |

## 2. 环境

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 本地能过 CI 挂 | 环境不一致，排查成本高 | 环境声明化，关键配置对齐并可核对 |
| 测试环境 schema / 配置与生产不同 | 结论不可迁移（尤其数据与鉴权类） | 差异清单化，在结论里声明前提 |
| 依赖外部真实服务 | 外部抖动即测试失败 | 边界处 mock，契约另测 |
| 密钥硬编码在测试里 | 泄露风险 | 走环境变量 |
| 数据量级与生产差数量级 | 性能与锁类风险测不出 | 相关风险处置改 `monitor` |

## 3. 执行

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 只在本地手动跑 | 改动没人守 | 接 CI（配置归 playbook/ci.md） |
| 全量套件才能跑 | 反馈慢，开发绕过 | 分层执行：快的每次跑，慢的定时跑 |
| 无超时设置 | 挂住的用例拖死流水线 | 用例与套件级超时 |
| 串行跑到几十分钟 | 同上 | 分片并行 |
| 没有失败快速反馈 | 等全跑完才知道 | 关键用例前置 |

## 4. 结果与可诊断性

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 失败只有一行 timeout | 无法定位，最终被标记 skip | 开 trace / 截图 / 视频（配置归 playbook） |
| 无 artifact 留存 | CI 上的失败无法复盘 | 失败时上传 artifact |
| 前后端日志无法串联 | 分不清是前端问题还是后端 | traceId 贯通（方案归 playbook/observability.md） |
| 报告无人看 | 红了也没人管 | 失败通知到人，且有响应时限 |

## 5. 门禁

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 没有门禁，红了也能合 | 测试沦为装饰 | 定哪些必须绿（至少：单测 + 核心链路 E2E） |
| 门禁一刀切全量必绿 | flaky 一多就被整体关掉 | 分层门禁：稳定层强制，探索层只报告 |
| 长期开着 retry 掩盖 flaky | 真问题被重试掩盖 | flaky 单独统计并限期修（判定线归 playbook/flaky.md） |
| 覆盖率当唯一门禁 | 刷覆盖率不刷有效性 | 覆盖率只做辅助，主门禁看关键路径与风险闭环 |

## 6. 维护

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 没人负责修挂掉的测试 | 逐步全被 skip | 明确 owner 与响应时限 |
| skip 无到期机制 | skip 永久化 | skip 必须带原因与复活条件 |
| 测试随 UI 频繁改动 | 维护成本超过收益 | 用 anti-rot 指标度量（归 playbook/anti-rot.md） |
| 无退役机制 | 无效用例越堆越多 | 定期按价值清理（判级归 e2e-test-quality） |

## 7. 有效性（最常缺的一环）

前六环都健全，这一环缺失，整套东西仍然可能抓不到 bug。

| 缺口信号 | 后果 | 该产出的义务 |
|---|---|---|
| 从未验证过测试能抓 bug | 全绿但无保护力。学术综述（arXiv 2511.21382）指出这正是自动生成测试的通病：能跑、覆盖率好看、**弱故障检测** | 对关键路径做故障注入：手工改坏实现，看对应测试是否变红 |
| 断言只判「不报错」 | 静默错误（算错但不抛）全漏 | 补结果判据（见 `oracle-patterns.md`） |
| 逃逸缺陷不回溯 | 同类问题反复逃逸 | 每个逃逸缺陷问一句「哪条测试本该抓住它，为什么没抓住」 |
| 修复回滚后测试仍绿 | 这条测试是装饰品 | 回归测试必须验证「回滚修复即变红」 |

**推荐的低成本做法**：不做全量变异测试（前端 E2E 每个变异体重跑整套，成本不可接受）。定向做——选 P0/P1 风险对应的实现点，手工植入该 `failure_mode` 描述的故障，看测试是否变红。这就是 Meta ACH（FSE 2025）思路的轻量版：先说清要防的故障长什么样，再验证判据抓不抓得住。

一次覆盖三五个关键路径就能暴露出大问题，比补一百条新用例有用。

## 产出形态

不要输出「现状体检报告」。输出的是排序后的缺口义务：

| 环节 | 缺口 | 后果严重度 | 处置 | 义务 |
|---|---|---|---|---|
| 有效性 | 核心支付链路从未验证过能抓 bug | 高 | design-fix | 对 3 条 P0 路径做定向故障注入，验证测试变红 |
| 门禁 | 无门禁 | 高 | design-fix | 单测 + 支付 E2E 设为合并必绿 |
| 数据准备 | UI 造数 | 中 | test | 改 API 造数 |

排序按「后果严重度 × 修复成本」，先给高收益低成本的。缺口一次别列超过 7 条——列 20 条等于没列。
