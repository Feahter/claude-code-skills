# 失效模式：配置、依赖升级与重构

适用：改配置 / 环境变量 / feature flag / CI 配置、升级依赖、纯重构。

**为什么这三类合一张卡**：它们的共同点是**都声称不改变业务行为**——所以最容易被跳过测试（"就改了个配置""只是 bump 版本""没动逻辑"）。而它们的失效形态也共享一个特征：**行为悄悄变了，但没有任何人在看**。因此核心 oracle 取向都是参照对照（变更前后行为一致）。

这类变更的风险不在于"改错了"，在于"改对了但改的不是你以为的那个东西"。

## 配置变更

- **配置项被删或改名，代码仍读旧键** → 读到 undefined 后落到默认值，静默降级。**整体重写配置文件时最高发**（原有的某项被漏掉，而不是被改错）
- **默认值兜底掩盖缺失**：`config.x ?? fallback` 让"没配"和"配了这个值"无法区分
- **环境间不一致**：测试环境有这项、生产没有（或值不同），结论不可迁移
- **数值单位歧义**：超时 `30` 是秒还是毫秒；大小 `100` 是 KB 还是条数
- **feature flag 组合未穷举**：单个 flag 都测过，A 开 B 关的组合从没跑过
- **flag 残留**：功能已全量，flag 还在，走的是哪条分支没人清楚
- **配置项之间的隐含依赖**：改了 A 必须同时改 B，但没有任何地方声明这个约束
- **热更新与重启语义不同**：改了不生效 / 只有部分实例生效 / 需要重启但没人知道
- **密钥与凭证轮换**：新值已下发，旧值仍被缓存或被某个实例持有
- **格式或解析器变更**：yaml → json、注释被丢弃、数字被解析成字符串
- **权限与角色配置**：角色定义变更后，既有用户的实际权限集合变了

## 依赖升级

- **破坏性变更未读 release notes**：主版本升级的必查项，跳过就是赌
- **语义化版本不可信**：patch 版引入行为变化是常态，不是例外
- **传递依赖的变化**：`package.json` 只改了一行，lock 文件里几十个间接依赖变了——**间接依赖的变化比直接依赖更危险，因为没人在看**
- **peer 依赖冲突**：装了两份同名库，运行时用的是哪一份不确定
- **类型定义变化**：编译通过但运行时行为不同（类型只约束编译期）
- **默认参数 / 默认行为变化**：最难发现的一类，代码一字未改而行为变了
- **安全补丁附带行为收紧**：修漏洞的同时加了更严格的校验，原本能过的输入现在被拒
- **产物变化**：polyfill 集合、tree-shaking 结果、bundle 体积、新增的外部请求域名
- **lock 文件未提交或与 package.json 不同步**：本地能跑 CI 挂，或反过来
- **构建工具链升级**：产物差异不体现在源码 diff 里

## 重构

- **行为漂移**：抽取函数时漏了某个分支、某个 early return、某个副作用
- **求值时机变化**：惰性变立即（提前触发副作用）、同步变异步（时序全变）
- **引用语义变化**：原来共享同一个对象，重构后是副本（或反之），调用方的修改不再互相可见
- **错误传播路径变化**：原来抛异常，现在返回 null / 空数组，调用方的错误处理静默失效
- **副作用顺序变化**：两个操作换了顺序，在有依赖时结果不同
- **边界条件被"顺手简化"**：看起来冗余的判断其实在挡某个真实场景
- **死代码删除误删**：实际有动态引用（字符串路由、反射、配置里的类名）
- **无测试覆盖的重构**：这不是风险，这是裸奔。重构的前提是先有参照

## 常用 oracle

| 风险类型 | oracle 取向 |
|---|---|
| 配置项是否真生效 | **可观测信号**：启动时输出实际生效值，断言它等于预期。**不要断言配置文件的内容**——文件对不代表读到了 |
| 关键配置缺失 | **必须失败**：缺失时启动失败并报明确错误，而不是静默取默认值 |
| 配置项被漏掉 | **参照对照**：重写配置前后，逐键比对生效值集合，差集必须为空或全部是有意的 |
| flag 组合 | **边界**：关键 flag 的组合矩阵每格至少有一次通过记录 |
| 依赖升级 | **参照对照**：升级前后对同一批输入的输出逐条比对（这是唯一可靠的判据） |
| 传递依赖变化 | **可观测信号**：lock 文件的 diff 被人读过并记录结论，不是"CI 绿了就行" |
| 产物变化 | **边界**：体积、外部域名、polyfill 集合不超过基线（守护方案归 `playbook/references/contracts.md`） |
| 重构等价性 | **参照对照**：重构前建立的特征测试（golden / 快照）在重构后逐条相等 |
| 引用语义 | **不变量**：调用方持有的引用在被修改后，另一方的可见性符合原有约定 |
| 错误传播 | **必须失败**：原本会报错的输入，重构后仍以同样的方式报错 |

## 证据来源

| 要找什么 | 去哪找 |
|---|---|
| 配置读取点 | grep 配置键名（**重点看有没有 `?? 默认值` 兜底，那会让缺失不可见**） |
| 被漏掉的配置项 | 配置文件的 `git diff`，逐键比对增删；重写型改动必须做全键集合对比 |
| 环境差异 | 各环境配置文件对比；CI 里注入的环境变量清单 |
| flag 现状 | flag 定义处 + 实际读取处；哪些 flag 已全量但未清理 |
| 依赖真实变化 | **lock 文件的 diff**（不是 package.json）；`npm ls <pkg>` 看实际版本树 |
| 破坏性变更 | 依赖的 CHANGELOG / release notes / migration guide |
| 重构的安全边界 | 被改动代码**当前有没有测试覆盖**——没有覆盖就先建参照，再重构 |
| 影响面 | codebase-memory `trace_path` 查被重构符号的调用方；LSP `findReferences` 复核 |

**最高性价比的两次检查**：一是配置重写型改动做全键集合对比（能直接查出被漏掉的项）；二是看 lock 文件 diff 里间接依赖的变化范围。这两条几乎每次都有结论。

## 可测试性阻塞信号

- **配置只在生产才有真值**（密钥、真实域名、真实限额）→ 相关风险处置改 `monitor`，写进不覆盖范围
- **没有"变更前"的参照**（重构一步到位、旧实现已删）→ 参照对照 oracle 全部失效。正确动作是 `design-fix`：**先建特征测试再重构**，而不是重构完了想办法验
- **配置读取分散无统一入口** → 无法断言生效值，属 `design-fix`（收敛到配置模块）
- **依赖的行为变化无法在测试环境复现**（依赖真实外部服务）→ `monitor`
- **构建产物差异无基线** → 产物类判据无从比对，先建基线

## 这一类最诚实的结论

配置和依赖类变更，**测试往往不是最优手段**。配置错误更适合用「启动时校验 + 生效值可观测」来消除，依赖升级更适合用「参照对照 + 产物基线」来守。所以这张卡产出的处置里 `design-fix` 和 `monitor` 通常多于 `test`——这不是偷懒，是把手段匹配到失效形态上。
