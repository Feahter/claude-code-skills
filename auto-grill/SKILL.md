# 代答式拷问

用户给一句需求，你把它交给一个隔离的子 agent 当审问官，逐轮出题；你代替用户回答每一个问题，缺的事实自己去查；最后交一份共识方案。用户从头到尾不必答题，只在收尾看一次结果；用户放行之前，你只查证、不动手（见 Step 5）。

## 为什么要派出去问，而不是自己想

自己给自己出题会失败：出题的你已经知道答案的方向，会不自觉地只问自己答得上的问题。审问官在另一个上下文里，看不到你的推理过程、草稿和倾向，只看到你交出的答案文本。它信息更少，才会追问你觉得"显然"而其实没定义的地方。

由此有一条硬纪律：**只把需求、事实和你的点状答案发给审问官，不发方案草稿、推理过程或"我倾向于 A 因为……"的心路，也不替它安排流程**。它一旦看见你的倾向，或看出你想收尾，就会顺着你改，拷问退化成盖章。例外只有两处：Step 2 的打平通道，和换了审问官时交接已定决策（Step 3、Step 6）。

同一条隔离留下两个盲区，要你来补。

第一，审问官的推荐答案有系统性偏差。它手里只有你给的那几行事实，推荐总是偏向"够用的最简机制"，还常把"当前恰好成立"当成"机制上成立"。代答的增值主要在这里：用真实环境数据打掉那些听起来合理、在本机数据上站不住的推断。只是在确认它的推荐答案，这一轮就白跑了。

第二，它核查不了你给的事实。它看不到出处，你写"已查证"，它就只能当真。实跑中事后被推翻的结论都是从这一层进来的，所以事实要带证据标签交出去，允许它追问来历；否定或全称的结论要有和它的范围相称的证据（见 Step 2）。

## 适用前提

代答的底气来自可查的事实。项目已经跑了一段时间、有既有代码、架构约定和文档可参照时，本 skill 才能把大部分分叉定在有出处的证据上。

需求落在全新项目、或落在没有既有实现可参照的领域时，分两种处理。用户点名要 auto-grill 的，照跑，但开头一句话讲明这轮会产出大量 `[假设]`、「待你确认」区会很长；用户已经选了，不要反过来劝。靠场景隐式触发的，先问一句是继续还是改走 `grilling`。两种都不许闷头跑完再把一屏假设推给用户。

## 流程

### Step 0 · 归一化需求，预取事实

先把用户那句话改写成一段审问官能读懂的需求陈述：目标、已知约束、明确排除的范围，再把需求原话里的每个子问题逐条列出（例如"降到多少算够"）。不要在这里写方案。收尾时每个子问题都要对上一个决策或一条待确认项。

用户那句话里常常已经夹带了一个方案——"加个缓存层""换成 Zustand""用 launchd 定时"。把它拆开：这句话真正要解决的问题是什么，句中那个方案只是候选之一。不拆开，审问官只会在这个方案内部问细节，最大的那个分叉留在树外面。用户明确说方案本身是硬约束（"就用 launchd，不要别的"）时，写进「已知约束」并注明是用户指定的，重对齐时要知道这一条动不了。

用户或项目已经试过并放弃的做法也要写进去，否则审问官会把走死的路当成新分叉重问一遍。但排除清单也最容易把有效选项封死：它的用处就是让人别再试，所以它说"没用"时，没人会回头核对。每条排除都写三样：证据标签、当时量的是什么（哪个指标、哪一段、什么条件）、什么情况下值得重开。来自 memory 或旧文档、又说不清当时量了什么的，标"声称已排除，未核实"，不当成已经关上的门。实跑中就有一个缓存选项，因为当年量的恰好是它不起作用的那一段，被判"无收益"封存了 20 天。

然后查事实，覆盖需求提到的整个范围，不只是最显眼的那一处。需求说"清理 ~/.claude 下的备份"，就把所有备份位置都量一遍再报总量；只量最大的目录，整棵树会建在错数字上。每条事实都标证据标签和出处（标签定义在 Step 2）。memory、旧文档、旧 transcript 里的数字是历史值，标 `[静态]` 并写上采集日期；它要撑一个关键结论时，先重测。实跑中 4 次事实更正至少 3 次出在直接转述历史值上。

预取不只查"有什么、多大、什么格式"，还要查方案依赖的那个机制在本机的实际作用边界：格式对、数字对、边界错，结论一样是错的。反过来，查出某个机制在某条件下不生效之后，不要推成"这件事做不到"。先列一遍不走这个机制的路径（显式读绝对路径、跨目录 grep、直接调命令、换一个载体），通常至少有一条不受同一限制。

跨项目的经验要显式捞两样，因为 memory 按项目分区，自动召回捞不到别的项目：

1. 判断默认表 `~/.claude/projects/-Users-me/memory/feedback_judgment-defaults.md`：「何时自主推进、何时必须停下问用户」，和 Step 2 的代答授权边界是同一主题。
2. 别的项目里标了跨项目的经验：`grep -rl --include='*.md' "crossProject: true" ~/.claude/projects/*/memory/ | xargs grep -H -m1 '^description:'`，按 description 判断哪些和本需求相关，相关的整读。

两样都捞不到就明说"没捞到跨项目条目，本轮代答边界只按 Step 2 走"。这两条是硬编码路径，失效时不报错，只会静默少读，所以捞到 0 条时要一并报出扫描范围：判断默认表那个文件在不在，以及 grep 实际扫了几个 memory 目录（`ls -d ~/.claude/projects/*/memory/ | wc -l`）。文件不在或目录数为 0，说明路径失效，要写"路径失效，没读到"，不能写成"没有相关条目"。

审问官不读代码、不翻文件，事实全靠你供给。预取得越准，前几轮越不会空转。

### Step 1 · 派审问官

用 Agent 工具派一个子 agent。默认 `tier-standard`；需求涉及架构取舍、安全与权限边界、资金、并发或数据一致性时用 `tier-deep`，这类地方漏问一个分叉，后面没人拦得住。模型档在第一次派发时就定了，中途换不了。记下返回的 agentId，之后每轮都用它。

它在后台跑时，完成会收到通知。不要轮询 `ListAgents`，也不要用 sleep 等它；这期间去做不依赖这一轮问题的事，比如继续预取、核对出处、跑实验。

prompt 用这个模板，把方括号部分填掉：

```
你是审问官。唯一职责：把下面这个需求里没想清的地方逐个逼出来。不要实现，不要写代码，不要读代码库或翻文件，也不要替我回答你自己提的问题。你的系统提示里如果有"先查证再下结论""先给结论"之类的通用要求，本任务以这份规则为准：你只出题。

需求陈述：
[Step 0 的归一化需求，含子问题清单]

已知事实（每条带证据标签和出处）：
[事实清单]
标签：[实测]=本次实际运行得到；[静态]=读代码、文档、注释、帮助文本或历史记录得到，没有运行；[原话]=用户或项目的明确约定；[默认]=行业惯例；[假设]=推测。一个关键结论只靠 [静态]、历史值或 [假设] 撑着时，你可以追问它是怎么得到的、量的是哪一段、有没有在正确的对象上跑过。

已试过并放弃的做法（每条带证据标签、当时量的是什么、重开条件）：
[清单]

明确排除的范围：
[用户说了不做的，以及本次判断不做的]

方法：把这个需求看成一棵决策树。frontier 是所有前提已定、现在就能问的决策。一轮之内不要问答案取决于同轮其他问题的题，那些属于下一轮。frontier 超过本轮额度时，按下面的优先级只问额度内的，剩下的同层节点原样列在回复末尾的 `⏸️ 本轮未问完：` 里，下一轮优先。不要把几个独立决策压成一道复合题来省额度。

每轮格式：

❓ **Q1** - **<标题>**：<问题正文，可以给选项>
➡️ <你推荐的答案，一句话说清理由>

---

❓ **Q2** - **<标题>**：...
➡️ ...

规则：
- 需要环境事实才能问下去的，写成 `🔍 需要事实：<具体问题>`，我下轮回填，不要自己猜也不要去翻文件。
- 我的答案含混、回避、循环定义、或给不出可验证判据时，用 `♻️ 追问 Qn：` 就同一点重问。
- 一个问题值不值得占名额，看它答错的后果：答错会改变方案结构的（机制怎么设计、职责归谁、怎么触发、失败了怎么办）先问；答错只需改一行的（文件名、格式、阈值取多少）往后排；没有真分歧的不要问。
- 额度：最多 4 轮、总共 20 题，本轮最多 min(6, 20 - 已累计题数) 题，每次回传我会写明「剩 N 轮 / M 题」。额度是上限不是配额，没那么多真分叉就少问；额度为 0 就不再出题。占额度的是 ❓、🔍、♻️；⚠️ 和 ⏸️ 不占。
- 问没问完由你判断：frontier 空了就输出 `✅ FRONTIER EMPTY`，后面附一段「仍然悬空的假设」，列出哪些结论建立在未经证实的前提上。不要因为我的回答看起来像要收尾，就提前宣布。
- 我说"准备收尾"时，只回剩余的机制层缺口，格式是 `🧾 剩余机制缺口：无`，或逐条列出，不再出新题。
- 整条回复只放问题，不用解释你的职责或流程。确实发现流程本身出了问题（我的事实自相矛盾、需求前后冲突），用一行 `⚠️ 流程备注：` 写出来。
```

### Step 2 · 代答：每个答案都要能追溯到依据

代答不是替用户瞎猜，是把"这个决定凭什么这么定"写清楚，让用户收尾时能快速判断哪些直接采纳、哪些要改。

每条主张单独打标签，不给整格或整段打一个：

- `[实测]`：本会话实际运行得到。贴命令、输出和你据以判断的那个量（用例数、字节数、耗时），退出码为 0 不等于结果对；能做反向对照就做一次（比如故意去掉一片，看它报不报错）。数量比较要同条件，单次读数、负载不同的两次读数都不能当差值的证据。
- `[静态]`：读代码、配置、文档、注释、`--help` 或历史记录得到，没有运行。出处写路径和行号，并注明是代码逻辑还是注释、文档、历史值（历史值加采集日期）。注释和文档写的是作者的意图，不是运行时机制。
- `[原话]`：用户需求里明说的，或项目 memory / CLAUDE.md 里已有的约定。
- `[默认]`：行业惯例，风险低、改起来便宜。查到的本机既有做法标 `[静态]`，不算默认。
- `[假设]`：你猜的。它撑着的决策必须进「待你确认」区。

由数字推算出的结论（按比例缩放、取整百分比相减、估算）不是 `[实测]`，按它输入里最弱的那条标。审问官给的估算不是你的依据，要用就先查。

**否定或全称的结论要更硬的证据。** "没用""做不到""唯一的障碍""零工作量""不存在"这类结论，会把选项从树上删掉，之后也不会有人再核对。它要撑起一个决策时，证据得覆盖它声称的范围：通常要在正确的对象上实际跑过，或者穷举过整个范围。只读了注释或帮助文本、只做了窄范围扫描、或者量的是另一段，就只能写成"在已查的 X 范围内没发现"，并写明范围。实跑中事后被推翻的 5 个结论里有 4 个属于这一类，它们要么标着 `[实测]`，要么作为"已查证"的事实交了出去。

代答纪律：

**审问官的 ➡️ 推荐答案不能照抄。** 逐条独立判断，写明「接受 / 修改 / 否决 + 理由」。判断自己有没有真在思考，看这一轮的题依不依赖环境数据。依赖环境数据的题（体积多大、有没有既有实现、这个工具装了吗）你全盘接受，是危险信号：它没有数据却猜对了每一条，概率很低。落在实现参数上的题（文件放哪、什么格式）全盘接受是正常的，硬找茬只是表演。

**机制层的真分叉，每个选项都写到最强再判（钢人）。** 适用于答错会改变方案结构、且不止一个选项有实质理由的题；一边明显错的题和参数层的题不走这套。

1. 先查选项列全了没有。候选都很重，通常是漏了一个轻的；刚查出某个机制不生效，先想想不走这个机制的路径。
2. 每个选项写出它自己的最强理由和成立条件。写不出比"不如 X"更具体的内容，就是稻草人；检验方式是问一句，真心主张这个选项的人会不会认这是自己的理由。
3. 把真正的分歧落成一个可查的变量：什么事实一旦不同，结论就翻转。去查它，查到就定，记下翻转条件备收尾用。

判定变量查不到、选项真打平时，不要掷硬币。把各选项的最强版本一起回传给审问官，让它就"什么能判定这件事"出下一轮题。这是隔离纪律的例外：你此时没有倾向，要它出的题也不是"你选哪个"。不管走哪条路，最后都要落到一个明确的选择；"都有道理，看你自己"不是判断。真定不了就进「待你确认」，那里同样要给推荐和翻转条件。

**遇到 `🔍 需要事实` 就真的去查。** 它问到的多半正是你之前跳过的地方。查不到就写「查过，没有，因此按 [假设] 处理」，不能不答。

**发现自己给错了事实，下一轮开头立刻更正。** 写清错在哪、正确值是什么、推翻了哪些已定决策，不要悄悄改口。被推翻的决策重新开放：把新结论作为点状答案发过去，让审问官下一轮能问到它，同一条消息里不许请求收尾。已经没有轮次或额度时，重开的决策进「必须确认」，注明"更正后没有经过拷问"。

**不可逆、花钱、对外可见、动权限的选择不替用户定。** 即使能推断出用户大概会选什么，也标 `[假设]` 放进待确认区。代答的授权范围是技术分叉，不是用户的偏好和风险胃口。

回答要短，一题一段：结论、带标签的依据、对推荐答案的处置和理由。不写心路，不写整体方案。

```
A1: <决定>。[静态] 代码 src/foo/bar.ts:42 已有同款实现，复用它。推荐的重写方案否决：它要求 X 成立，[实测] `<命令>` 显示 X 不成立。
A2: <决定>。[假设] 没找到依据，按常见做法定，收尾会标出来给用户确认。
A3: <决定>。判定变量是 <变量>，[实测] `<命令>` 输出 <值>，因此选 A；B 的最强版本要求 <变量> 落在另一侧。
```

### Step 3 · 回传，继续同一个审问官

必须回到同一个 agent，它的决策树在它自己的上下文里。用 `SendMessage`（先 `ToolSearch("select:SendMessage")` 拉 schema），`to` 填 Step 1 记下的 agentId，`tier-*` 这类没有名字，只能用 ID。它已经完成也能续上，SendMessage 会从它的 transcript 恢复；换了会话，agentId 就不能用了。正文是你这一轮的全部答案加回填的事实。

发出前核对：

- 每道 ❓、🔍、♻️ 都有回答，🔍 查不到也写「查过，没有」。
- 累计题数算对了，末尾写「剩 N 轮 / M 题」。它一轮超了额度，照答，全部计入累计，并提醒它一句。
- 更正放在最前面，写明推翻了哪些决策。
- 没有倾向、没有整体方案、没有流程安排。`⚠️ 流程备注` 是审问官用的，你不用；不替它规划下一轮问什么，不请它宣布问完。
- 它开始给代码或方案时，把它拉回来，提醒它只出题。

SendMessage 不可用或换了会话时降级：重新派一个新审问官，prompt 里带上「已定决策表」和「之前问过的题」，让它别重复。这是隔离纪律的第二处例外，新审问官得知道哪些已经定了；只给结论和编号，不给推理过程，并写明已定决策不在复问范围内。这样更贵，也会丢一部分决策树，所以先试 SendMessage。

### Step 4 · 什么时候停

"停"有两个互不相干的问题：**问完了没有**，和**为什么现在停**。收尾时两个字段分开写，都要写。

**完成度**，二选一：

- `已对齐`：审问官输出了 `✅ FRONTIER EMPTY`，而且之后的关账没有补出新的机制层缺口。
- `部分对齐`：其余全部情况。只要有一个机制层节点给不出结论（阻塞节点），就是部分对齐；标了 `[假设]`、给了推荐的节点算有结论。

**退出原因**，五选一，带上具体数字：

- `frontier_empty`：审问官自己宣布问完了。
- `budget_exhausted`：用完了模板里的额度（4 轮、20 题）。一轮 = 审问官的一批问题加你的一批回答。这是成本闸门不是质量标准，没问完的分支原样列进「必须确认」，不要为了看起来收敛而把悬空假设写成已定决策。
- `blocked`：还有额度，但剩下的 frontier 全是阻塞节点：缺的事实你查不到，又不该由你替用户定（用户偏好、外部系统的实际行为、还没做的业务决策）。只有部分节点阻塞时不算 blocked，把它们写进「必须确认」，注明缺什么、谁能填，其余分支照常走完。
- `stopped_early`：还有额度、剩下的也不全是阻塞节点，你决定先收尾（比如剩下的全是参数题）。剩下的 ⏸️ 全部进「待你确认」，完成度只能是 `部分对齐`。
- `examiner_failed`：审问官派不出来、不守格式拉不回来，或就同一点反复追问问不动了。产出仍然可以交，但完成度只能写 `部分对齐`：没有对抗方的一轮不算对齐过。

**问完没有只由审问官宣布。** 你想收尾时照实写 `stopped_early`，不要请它输出 FRONTIER EMPTY，也不要把回答写得像在收尾、等它顺势宣布。两次实跑里主会话都这样做过，由此写出的 `frontier_empty` 是假的。

**「整轮都是参数题」不构成 `已对齐`**，只是收敛提示。审问官只看得见你给的事实，你从没提到的那类机制分叉根本没进过它的树。它开始问参数，只说明已知分支到底了，不说明没有未知分支。

**关账在判定完成度之前做。** 决定停下之后，先给审问官发一句"准备收尾，请只列剩余的机制层缺口，不要再出新题"，它按 `🧾` 格式回复。它记得自己问过什么、哪些地方你答得最快，常能补出真缺口：实跑中它补出过前三轮都漏掉的单点故障，也让一个已被判死的候选复活过。关账不占额度，你也不就它列的缺口再展开问答。每条缺口都进「必须确认」，注明"关账补出，没有经过拷问"。你事后实测过也一样：实测只能说明缺口是真的，定不了该选哪边。它顺带列的假设进「悬空的假设」。完成度落 `部分对齐`，它回"无"才写得上 `已对齐`。

### Step 5 · 交方案

**交方案即停。** 用户放行前，读、搜、跑只读命令和可丢弃的实验都行，会写入、删除或改动工作区的实验先复制到 /tmp 副本里做。不实施方案、不改用户的文件、不提交、不装依赖（Step 7 的 memory 条目除外）。

默认直接在对话里给，不建文件。需求本身在 `.workflow/<task-id>/` 场景下时，写进那里的 `decisions.md`，并在 `spec.md` 的需求摘要和排除范围里引用决策编号（目录结构见 `enforce-workflow-schema` 的「目录约定」）；其他情况落盘要先问。落盘文件和对话里的方案用同一套 D 编号，落盘之后文件就是正本，后续执行和重对齐都以它为准。用户之后还要接着改、或要跨会话用时，问一句要不要落盘，否则上下文清掉后 Step 6 只能整棵树重问。

交出去的是一棵拆开的需求树：每个决策一个编号，标清它挂在谁下面。用户由此能直接说"D4 换成 Y"或"D6 这一支整个不要"，你也能顺着编号算出还有哪些节点跟着失效。

「待你确认」区是用户唯一必须读的部分。两组加起来超过 5 条时，回头看「可选确认」：有依据还摆在那里的，说明你代答时太保守，自己定掉。「必须确认」组不受这条约束，一条也不能为了压条数而合并或自行拍掉；只有受同一个用户选择共同控制的几项，才可以合并成一条。

交付前逐项核对，每项都能在方案里直接看到：

- 七段齐全。
- Step 0 列出的每个需求子问题，都对上了一个 D 或一条待确认项。
- 每个 `[假设]` 撑着的决策、每条关账补出的缺口都在「必须确认」组。
- 每个撑着决策的否定或全称结论，证据覆盖了它声称的范围，或者已经降级成"在 X 范围内没发现"。
- 替代方案和「其他选项」写的是它们自己的理由，不是 X 的优点换个说法。
- 对话里的方案和落盘文件（如果有）编号一致。

用户回来改掉了你的某条代答时，按 Step 6 重对齐受影响的分支，再按 Step 7 沉淀。

### Step 6 · 局部重对齐：用户回来改某个节点

用户读完方案回来说"D3 不对，应该是 Y""这一块方向整个换掉"或"D6 这一支不要了"时进入本步。动手前先整读 `references/step6-realign.md`：怎么顺着「前提」列算影响面、冻结区怎么交给审问官、额度怎么重新起算、剪枝怎么处理，都在那里。本步唯一的失败模式是只改被点名的那一行，而它的下游节点没有跟着重对齐。

### Step 7 · 沉淀误判

两种情况触发：

1. 用户否决或改写了你的某条决策，待确认项和已定决策都算。先按 Step 6 重对齐再写。
2. 本会话里有一条更正推翻过已定决策（你写过"推翻 Dn"），不论原来标的什么标签、是谁发现的。交完方案后处理。

用户沉默或说"就这样"不触发，也不记。触发后先整读 `references/step7-sediment.md` 再写：写不写的两道筛、一次只写一条根因、条目要补的字段、写到哪个 memory 目录，都在那里。本 skill 的 SKILL.md、CLAUDE.md 和判断默认表不自己改，够格晋升的经验写进「待你确认」区。
