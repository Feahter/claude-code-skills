# 代答式拷问

用户给一句需求，你把它交给一个隔离的子 agent 当审问官，逐轮出题；你代替用户回答每一个问题，缺的事实自己去查；最后交一份共识方案。用户从头到尾不必答题，只在收尾看一次结果。

## 为什么要派出去问，而不是自己想

自己给自己出题会失败，因为出题的你已经知道答案的方向，会不自觉地只问那些自己答得上的问题。审问官在另一个上下文里，看不到你的推理过程、草稿和倾向，只看到你交出的答案文本。正因为它信息更少，它才会追问你觉得"显然"而其实没定义的地方。

这条原理决定了一条硬纪律：**只把需求和你的答案发给审问官，绝不发你的方案草稿、推理过程或"我倾向于 A 因为……"的心路**。一旦它看见你的倾向，它就开始顺着你改，拷问就退化成盖章。

同一条隔离也造成了审问官的系统性偏差，你必须替它补上：它手里只有你给的那几行事实，所以它的推荐答案总是偏向"够用的最简机制"，并且经常把"当前恰好成立"当成"机制上成立"。它会说"这两条规则天然重合，不需要额外反查"——而你一跑 grep 就发现重合是偶然的。**代答方的增值几乎全在这里**：用真实环境数据去打掉那些听起来合理、但在本机数据上站不住的推断。如果你只是在确认它的推荐答案，这一轮拷问就白跑了。

## 适用前提

代答的底气全部来自可查的事实。项目已经跑了一段时间、有既有代码、架构约定和文档可参照时，本 skill 才能把大部分分叉定在 `[实测]` 上。

需求落在全新项目、或落在没有任何既有实现可参照的领域时，先告诉用户：这一轮代答会产出大量 `[假设]`，「待你确认」区会很长，收益不如他们自己答几轮。让用户决定是继续还是改走 `grilling`。不要闷头跑完再把一屏假设推给他们。

## 流程

### Step 0 · 归一化需求，预取事实

先把用户那句话改写成一段审问官能读懂的需求陈述：目标、已知约束、明确排除的范围。不要在这里就写方案。

用户或项目已经试过并放弃的做法要一并写进去，附放弃的理由。审问官只看得到你给的文本，漏掉这段它会把走死的路当成新分叉重问一遍，而你只能用"试过了，不行"回答——这一轮的名额就白花了。

然后查事实，**覆盖需求提到的整个范围，不是最显眼的那一处**。需求说"清理 ~/.claude 下的备份"，就把所有备份位置都 du 一遍再报总量，只量了最大的那个目录就下结论，会让审问官的整棵决策树建在错数字上，下一轮全部返工。查过的写进「已知事实」段，每条标来源（文件路径、命令输出）。

审问官不读代码、不翻文件，事实全靠你供给。预取得越准，前几轮越不会空转。

### Step 1 · 派审问官

用 Agent 工具派一个子 agent。默认 `tier-standard`；需求涉及架构取舍、安全与权限边界、资金、并发或数据一致性时用 `tier-deep`——这类地方漏问一个分叉，后面没人拦得住。模型档在第一次派发时就定了，中途换不了。

它在后台跑，完成时你会收到通知。不要轮询 `ListAgents`，也不要用 sleep 等它——这期间去做不依赖这一轮问题的事（继续预取事实、核对引用）。

prompt 用这个模板，把方括号部分填掉：

```
你是审问官。唯一职责：把下面这个需求里没想清的地方逐个逼出来。不要实现，不要写代码，不要读代码库，也不要替我回答你自己提的问题。

需求陈述：
[Step 0 的归一化需求]

已知事实（我已查证，可直接当真）：
[路径、版本、体积、既有实现、命令输出，每条带来源；含已试过并放弃的做法及其失败原因]

明确排除的范围：
[用户说了不做的，以及你判断本次不做的]

方法：把这个需求看成一棵决策树。frontier 是所有前提已定、现在就能问的决策。每轮把整个 frontier 一次问完，一轮之内不要问那些答案取决于同轮其他问题的题——那些属于下一轮。

每轮格式：

❓ **Q1** - **<标题>**：<问题正文，可以给选项>
➡️ <你推荐的答案，一句话说清理由>

---

❓ **Q2** - **<标题>**：...
➡️ ...

规则：
- 需要环境事实才能问下去的，写成 `🔍 需要事实：<具体问题>`，我下轮回填，不要自己猜也不要去翻文件。
- 我的答案含混、回避、循环定义、或给不出可验证判据时，用 `♻️ 追问 Qn：` 就同一点重问，别放过。
- frontier 空了就输出 `✅ FRONTIER EMPTY`，后面附一段「仍然悬空的假设」清单：哪些结论建立在未经证实的前提上。
- 一个问题值不值得占名额，看它答错的后果：答错会改变方案结构的（机制怎么设计、职责归谁、怎么触发、失败了怎么办）先问；答错只需改一行的（文件名、格式、阈值具体取多少）往后排，没有真分歧的不要问。
- 每轮问题数控制在 6 个以内，按上一条排序。6 是上限不是配额，没那么多真分叉就少问，宁可多一轮，不要一轮 15 题。
- 整条回复只放问题。流程状态我清楚，不用向我解释你的职责边界或"等待回答后再进入下一轮"。确实发现流程本身出了问题（比如我的事实自相矛盾、需求前后冲突），用一行 `⚠️ 流程备注：` 写出来，其余情况不写任何非问题内容。
```

### Step 2 · 代答：每个答案都要能追溯到依据

这是本 skill 的全部价值所在。代答不是替用户瞎猜，是把"这个决定凭什么这么定"写清楚，让用户收尾时能快速判断哪些可以直接采纳、哪些要改。每条答案标一个来源：

- `[实测]` 读了代码、跑了命令、查了官方文档得到的。门槛是能贴出路径或命令输出，贴不出就不是实测。
- `[原话]` 用户需求里明说的，或项目 memory / CLAUDE.md 里已有的约定。
- `[默认]` 行业惯例或本机既有做法，风险低、改起来便宜，可以直接定。
- `[假设]` 你猜的。必须同时进最终方案的「待你确认」区。

四条纪律：

**审问官的 ➡️ 推荐答案不能照抄。** 逐条独立判断，明确写「接受 / 修改 / 否决 + 理由」。它出题时信息比你少，推荐答案常常是合理但不适配本项目的那一个。

判断自己有没有真在思考，看的不是接受比例，而是**这一轮的题依不依赖环境数据**。依赖环境数据的题（体积多大、有没有既有实现、这个工具装了吗）你全盘接受，是危险信号——它没有数据却猜对了每一条，概率很低。落在实现参数上的题（文件放哪、什么格式、匹配规则怎么写）你全盘接受是正常的，那些判断本来就不需要环境数据，此时硬找茬只是表演。

**遇到 `🔍 需要事实` 就真的去查。** 它问到的多半正是你之前跳过的地方。查不到就写「查过，没有，因此按 [假设] 处理」，不要含糊带过。

**发现自己上一轮给错了事实，下一轮开头立刻更正。** 它的整棵决策树建在你给的事实上，一个错数字会让后面所有分支都偏。更正要写清错在哪、正确值是什么、以及这会不会推翻已经定下的决策——不要悄悄改口。

**不可逆、花钱、对外可见、动权限的选择不替用户定。** 即使能推断出用户大概会选什么，也标 `[假设]` 放进待确认区。代答的授权范围是技术分叉，不是用户的偏好和风险胃口。

回答格式简短即可，一题一段，带来源标签：

```
A1: <决定>。[实测] src/foo/bar.ts:42 已有同款实现，复用它。推荐答案里的重写方案否决，理由是……
A2: <决定>。[假设] 没找到依据，按常见做法定，收尾会标出来给用户确认。
```

### Step 3 · 回传，继续同一个审问官

必须回到同一个 agent，它的决策树在它自己的上下文里。用 `SendMessage`（先 `ToolSearch("select:SendMessage")` 拉 schema，不然调用会因缺参数报错），`to` 填 Agent 工具返回的 agentId——`tier-*` 这类没有名字，只能用 ID。正文是你这一轮的全部答案加回填的事实。

SendMessage 不可用时降级：重新派一个新审问官，prompt 里带上「已定决策表」和「之前问过的题」，让它别重复。这样更贵，也会丢一部分决策树，所以先试 SendMessage。

### Step 4 · 什么时候停

三种停法，性质完全不同。收尾时必须在方案头部写明是哪一种，别让「想透了」和「问不下去了」看起来一样。

**对齐通过**，任一条成立：

1. 审问官输出 `✅ FRONTIER EMPTY`。
2. **这一轮的题全部落在实现参数上**——文件放哪、用什么格式、匹配规则怎么写——不再动机制。这是最可靠的收敛信号，比轮数准：机制层的题会被环境数据推翻，参数层的题不会。看到整轮都是参数题，就在答完这一轮后收尾。

**名额用尽退出**：到了第 4 轮，或累计问题数超过 20。这是成本闸门，不是质量标准。撞到上限就停，把没问完的分支原样列进「待你确认」。不要为了看起来收敛而把悬空的假设写成已定决策。

**某个节点的缺口填不上**：这个分叉缺的事实你查不到，而它又不该由你替用户定（他们的偏好、外部系统的实际行为、还没做的业务决策）。这不是整轮失败，卡住的只有那一个节点：把它标成阻塞节点写进「待你确认」，注明缺什么、谁能填，其余分支照常走完。整轮停在这里才是浪费。

三种情况收尾前都要先把判断告诉审问官，要它只列还剩的机制层缺口、不要再补参数题。它手里有你没有的视角——它记得自己问过什么、哪些地方你答得最快，可能直接补出一条真缺口（实跑中就在这一步问出了"单项失败会不会让整套机制失效"这个前三轮都漏掉的单点故障）。它说没有了，收敛才算确认过而不是你单方面宣布的。

### Step 5 · 交共识方案

默认直接在对话里给，不建文件——用户没要求的文档不主动创建。需求本身就在 `.workflow/<task-id>/` 场景下时，写进那里的 `spec.md`。用户点名要文件时问清路径。

用户说了之后还要接着改、或这份方案要跨会话用时，问一句要不要落盘。Step 6 的重对齐要读回这张决策表，上下文清掉之后没有它就只能整棵树重问一遍。

交出去的不是一份清单，而是**一棵拆开的需求树**：每个决策一个编号，标清它挂在谁下面。用户由此能直接说"D4 换成 Y"或"D6 这一支整个不要"，而你能顺着编号算出还有哪些节点跟着失效。没有编号和前提关系的扁平表格，用户只能整体接受或整体推翻。

结构照这个来：

```
## 对齐状态
<对齐通过 | 名额用尽退出（第 N 轮，累计 M 题） | 有 K 个节点缺口待填>，一句话说明依据

## 需求（一句话）
<归一化后的目标，含明确排除范围>

## 已定决策
| # | 决策点 | 结论 | 前提 | 依据 | 被否决的替代方案 |
|---|---|---|---|---|---|
| D1 | <机制层的决策排前面> | | — | [实测] path:line | |
| D2 | | | D1 | [原话] | |
（前提列填这个决策依赖哪些上游编号，根节点写 —；依据列写 [实测]/[原话]/[默认] 和具体出处）

## 待你确认（我替你选了，但你可能有别的偏好）
1. [D3] <决策点>：我选了 X，因为……。如果你更看重 Y，应该改成 Z。
（所有 [假设]、所有不可逆或花钱或动权限的选择、所有填不上缺口的阻塞节点，都必须在这里，每条带它的节点编号）

## 悬空的假设
| 挂在 | 假设 | 怎么验证 | 不成立要重做哪块 |
|---|---|---|---|
（审问官列的 + 你自己知道没验证的。验证列写具体命令、试跑或该问谁，不要只写后果）

## 风险与验证
<按 ~/.claude/rules/risk-and-verify.md 定档，给出这一档要跑的验证命令>

## 明确不做
<本次排除的范围，防止后面被当成遗漏>
```

「待你确认」区是用户唯一必须读的部分。它不该是十几条大杂烩——如果超过 5 条，说明你代答时太保守，把本来能定的技术分叉也推给用户了；回头把有 `[实测]` 或 `[默认]` 依据的那些自己定掉。

用户回来改掉了你的某条代答时，流程上按 Step 6 重对齐受影响的分支；同时，被改的那一条是本次最值钱的产出：你标 `[默认]` 或 `[假设]` 的推断没对上他们的真实偏好，而偏好会在下一个需求里再次出现。按 `~/.claude/rules/workflow.md` 的沉淀纪律写一条 `feedback_*.md`，记清你当时凭什么那么定、被改成了什么。原样采纳的不必记。

### Step 6 · 局部重对齐：用户回来改某个节点

这一步不在首轮里，它在用户读完方案之后发生。用户说"D3 不对，应该是 Y"或"这一块方向整个换掉"时，既不要把整棵树重跑一遍，也不要只改被点名那一行。

1. **先算影响面。** 顺着「前提」列查谁以被改节点为前提，再查它们的下游，一直查到没有。这些节点连同挂在它们上的待确认项和悬空假设全部标为待重对齐，其余节点冻结。用户改的是靠上的节点时，不要假装只有那一条要动——这是本步唯一的失败模式，也是把"对整棵树迭代"退化成"改一行字"的地方。
2. **把冻结区和待重对齐子树一起交给审问官。** 首轮那个 agent 还活着就用 `SendMessage` 续上，它记得整棵树；正文写清：用户否决了 D3 的结论 X 改成 Y，只就 Y 为前提重问受影响的分支，冻结区的节点不要复问。agent 已结束时新派一个，prompt 里附「已定决策表（冻结，不要重问）」和「待重对齐的节点清单」。
3. **只走受影响的子树。** Step 2 到 Step 4 的纪律照旧，轮数和题数上限按子树规模重新起算，不累加首轮的额度。被改的节点换了前提之后，原先标 `[实测]` 的下游依据可能已经失效，要重新查一遍，别沿用上一版的结论。
4. **产出仍用 Step 5 的模板**，冻结区原样保留，只重写变动的节点。对齐状态那段注明这是第几次重对齐、改了哪些编号。

用户是剪枝而不是修正时更省事（"D6 这一支不要了"）：把那棵子树连同它的待确认项和悬空假设一起删掉，移进「明确不做」，不必再问审问官——剪枝不产生新分叉。

## 容易垮掉的几个地方

- **附和**：一轮里所有推荐答案全部接受。信息比你少的人给的建议不可能全对，全对说明你没在判断。
- **泄漏倾向**：在答案里夹带「我的整体方案是……」。审问官只该看到点状答案，看到全局图它就不再挑刺了。
- **拷问跑偏成实现**：审问官开始给代码或方案。把它拉回来，提醒它只出题。
- **把排除范围留白**：没写「明确不做」的方案，下次一定被当成漏了。
- **重对齐只改被点名的那一行**：下游节点的前提已经变了，还挂在旧结论上的都是错的，看起来只动一处其实留了一片矛盾。
