# Step 7 · 沉淀误判

两种情况触发：

1. 用户否决或改写了你的某条决策，待确认项和已定决策都算。先按 Step 6 重对齐再写：用户点名的节点常常只是症状，真正的错源在上游。
2. 本会话里有一条更正推翻过已定决策（你写过"推翻 Dn"），不论原来标的什么标签、是谁发现的。交完方案后处理。实跑中最有价值的那条经验就是这么来的，旧的触发条件接不住它，最后是用户开口要求才写下。

写之前先过两道筛。第一道：换一个任务，你还会再踩这个坑吗？答"不会"就不写。第二道：这个错误的形状，本 skill 已有的规则是不是已经管到了（比如历史值没重测、把注释当成机制）？答"是"也不写 memory，对齐状态里注明没守住哪条就够了，那是规则执行的问题，不是新经验。

用户沉默或说"就这样"不触发，也不记。这不等于"视为采纳"：[原话] `feedback_judgment-defaults.md` 的既有约定是「不记成功样本（沉默不算认可）」。所以多数运行产出 0 条经验是正常的；已定决策里错了却一直没人发现的那些，这个机制本来就覆盖不到。

一次运行只写一条，几个错误合成一条根因：重复条目会稀释真正有信息的那条，还会吃 `MEMORY.md` 的常驻预算。根因不一定落在某个 D 上，它可能在 Step 0 把需求里夹带的方案还原错了，也可能在预取时漏了一个作用边界；硬锚到最近的 D 上，写出来的就是症状。

条目按 `~/.claude/rules/workflow.md` 的沉淀纪律写，格式沿用既有 `feedback_*.md`（frontmatter + **Why** + **How to apply** + `[[双链]]`，`description` 那行就是摘要，正文不依赖方案原文）。额外补两样：涉及的决策编号和它当初的证据标签；错误最早出现在哪一步（例如 Step 0 转述的历史值、某一轮代答、从没被问到的分叉）。后者只是存在性记录，不要累加成准确率、置信度或任何分数。

**写到哪里**：系统提示里给出的那个 memory 目录（它就是当前项目的，不要自己从 cwd 推 slug），并在它的 `MEMORY.md` 加一行索引。然后自问"换一个完全不同的项目，这条还成立吗"，成立就在 frontmatter 补 `metadata.crossProject: true`，Step 0 的跨项目 grep 靠这个标记把它捞回来。不要为了跨项目把条目写进别的项目的 memory 目录（包括 `-Users-me` 那个），别的项目召回不到它。

**不自己改规则**：本 skill 的 SKILL.md、CLAUDE.md 和判断默认表都影响所有项目，超出代答授权。一条经验看起来够格晋升成默认规则时（按判断默认表里的非对称闸门：变得更保守，单次即可；变得更激进，要同类证据 ≥2 次或用户明说），写进「待你确认」区，由用户决定是否落笔。
