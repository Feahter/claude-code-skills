# Skill 正文

把本次会话暴露的问题写回某个 skill 的 `SKILL.md` 正文或它的 references，让它下次表现更好。

## 先分去向

- 问题出在某个 skill 的做法上，比如步骤漏了、判据错了、用户纠正过它的输出：写进那个 skill，按本卡处理。
- 要记的是协作偏好、项目事实或判断方式：不改 skill，主会话按 CLAUDE.md「经验主动沉淀」写进 memory。
- 两个 skill 抢同一类任务：这是分工问题，不是正文问题，主会话直接重划边界。

## 改之前先判这份文件的命运

先 `ls -la ~/.claude/skills/<name>` 看它属于哪一类：

| 类型 | 判别 | 改正文的后果 | 做法 |
|---|---|---|---|
| 实体目录 | 没有 `->` | 立即生效，不会被更新覆盖 | 直接改 |
| 软链到 `~/.agents/skills` | 有 `->`，多半登记在 `~/.agents/.skill-lock.json` | 生效。`update-skills.py` 以后会把它列为结构变更，只报告不覆盖，等于变成本地 fork。`~/.agents/skills` 同时是 Codex 的加载目录，改动也会进 Codex | 小改正文可以接受；只是调边界就改 CLAUDE.md 的消歧节 |
| plugin skill | 路径在 `~/.claude/plugins/` 下 | 下次 `claude plugin update` 会覆盖 | 不改本体，写进 CLAUDE.md |

## 从会话取证据

保留用户原话和失败的具体表现：报错信息、跑偏的那一步、用户纠正了什么。不凭印象概括成一条泛泛的规则。

## 写法

- 写进经验真正起作用的位置，比如对应的步骤、检查清单或 reference，不在文件末尾另堆一个「经验」章节。
- 写清为什么这样做，不只加一条 MUST。
- 改完按 SKILL.md「工作流程」第 5、6 步处理：先留回滚副本，再重放一次出问题的场景。只做了静态自检就如实说。
