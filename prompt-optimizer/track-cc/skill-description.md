# Skill Description

优化 `SKILL.md` frontmatter 中的 `description`。它的首要任务是帮助模型判断何时加载 Skill，而不是解释完整工作流。

## 检查重点

### 作用和范围

用一句话说明 Skill 能完成什么，以及它处理的对象。避免“强大的工具”“提升质量”一类无法区分 Skill 的描述。

### 真实触发信号

覆盖用户实际会表达的意图，包括必要的正式说法、口语说法、文件类型或任务场景。触发信号应描述意图，不要只堆关键词。

示例只在能补足难以概括的口语或边界场景时加入；不是每个 description 都需要引号包裹的 utterance。

### 区分相邻能力

当它容易与其他 Skill 争抢，或用户报告误触发时，说明最关键的边界。不要为了形式完整而罗列与当前 Skill 无关的“不适用”场景。

需要判断冲突时，读取同一作用域内相邻 Skill 的 frontmatter，只比较真实重叠的能力和触发信号。

### 简洁和可判定

description 常驻技能列表，应尽量短，但不能为了省 token 删除决定是否触发所需的信息。把执行步骤、输出模板和内部方法留在正文。

## 诊断触发问题

用户提供“应该触发但没触发”或“不该触发却触发”的原话时：

1. 保留原话，不先改写样本。
2. 判断样本表达的是能力范围、对象、动作还是边界信号。
3. 检查当前 description 是否缺少该信号，或被相邻 Skill 更强地匹配。
4. 样本较多或用户要求验证时，用新旧 description 做 should-trigger / should-not-trigger eval；不要把单个子 agent 的主观判断称为真实结论。

## 改写原则

- 保留 `name` 和其他 frontmatter 字段。
- 给出一份干净的完整 description，不在其中插入诊断标签。
- 同时写清“做什么”和“何时使用”，但避免复制正文。
- 只有真实近邻冲突存在时才写排除条件。
- 不用 `ALWAYS`、`NEVER` 代替清楚的触发条件。

## 输出

先指出影响触发判断的关键问题，再给完整改写。若已修改文件，报告验证结果即可，不必逐项列出通过项。
