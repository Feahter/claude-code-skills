# Anthropic API Prompt

优化应用通过 Anthropic API 发送的 `system`、`user` 或多轮消息内容。先区分 prompt 文本、请求参数、工具定义和应用逻辑；只检查用户实际提供的部分。

涉及具体模型或 SDK 行为时查询当前官方文档。不要沿用旧模型的 prefill、stop sequence、缓存或结构化输出技巧。

## 按需检查

### 任务和成功标准

模型是否知道要完成什么、基于哪些输入、怎样算正确。角色描述只在专业立场、权限或受众会影响结果时加入，不是 system prompt 的必选开头。

### 指令与数据边界

当 prompt 同时包含外部数据、示例或多段上下文时，用清楚的标题、Markdown、XML 或结构化字段分隔。简单 prompt 不必为了形式增加 XML。

对不可信输入，明确它是待处理数据而不是高优先级指令，并配合应用层安全措施；prompt 本身不能替代权限和输入校验。

### 输出契约

只有调用方需要解析固定结构时才定义 schema、字段和缺省行为。若当前 API / SDK 提供结构化输出，优先使用官方机制，而不是依靠 prefill 或随意的 stop sequence 拼出 JSON。

自然语言回答只需说明受众、篇幅或重点中真正影响结果的部分，不要把所有输出都改成 JSON。

### 示例

当规则难以文字说明、边界容易混淆或格式必须精确时添加少量代表性示例。示例数量由任务复杂度决定；简单任务可以没有示例。每个示例都应与当前指令和输出契约一致。

### 约束和不确定性

为高概率且高影响的错误写清边界，例如不得编造缺失事实、信息不足时返回什么。不要机械地为每条正向指令配一条禁止项。

### 冲突、重复和顺序

检查 system、user、示例和工具说明之间是否互相冲突，后文是否无意覆盖前文，同一规则是否重复多次。把最稳定的规则放在 system，把每次请求的数据留在 user 内容。

## 有失败样本时

仅靠静态扫描不能证明 prompt 会解决“JSON 漂移、幻觉、漏字段、拒答或风格不稳”等症状。用户提供输入和实际输出后：

1. 先判断失败来自 prompt、模型能力、采样参数、工具结果还是应用后处理。
2. 用能复现问题的样本建立基线。
3. 比较新旧 prompt，检查正确性、稳定性、token 和延迟；不要只展示一条成功样本。

## 输出

只报告与当前任务有关的问题，给出干净改写。用户同时提供调用代码时，可以检查参数，但对版本相关结论附官方依据；未提供代码时不要猜测 `temperature`、缓存、prefill 或 stop sequence 配置。
